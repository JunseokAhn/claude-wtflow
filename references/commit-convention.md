# 커밋 컨벤션

> **이 문서는 기본값이다 — 맨 아래 순위다.** 저장소나 사용자 쪽에 같은 항목을 정해둔 것이
> 있으면 그쪽이 우선한다. 어디를 보고 무엇이 우선하는지는 `${CLAUDE_PLUGIN_ROOT}/references/convention-precedence.md`.

커밋 메시지를 짓는 `commit`·`auto` 가 시작 전에 읽는다.

브랜치 이름·Step 모델·note 종류은 이 문서에 없다. `worktree-discipline.md` 를 본다.

## Subject

기본 형식은 [Conventional Commits](https://www.conventionalcommits.org) —
`<type>(<scope>): <제목>`. **저장소가 다른 형식을 쓰고 있으면 그것을 따른다.**

- `type` 은 그 표준이 정한 값 (`feat` / `fix` / `refactor` / `chore` / `docs` / `test` / `perf` / `style`)
- `scope` 는 도메인·기능 영역. 저장소가 이미 쓰는 표기를 그대로 쓴다
- **제목의 언어와 어투는 규정하지 않는다** — 쓰기 직전 `git log --pretty=%s -n 15` 로
  저장소가 실제로 쓰는 언어·어투를 보고 거기 맞춘다
- 72자 이내, 마침표 없음
- **식별자는 원문 유지** — 코드에 있는 이름(상수·함수·API·설정 키)은 번역하지 않는다.
  번역하면 검색이 안 된다

**이슈 제목도 같은 규칙이다** — 위 Subject 규칙을 이슈 제목에 그대로 쓴다. 한쪽만 고치면 어긋난다.

**사용자 CLAUDE.md 의 지시가 이 문서보다 우선한다** — 저장소·사용자 전역 순위와의 관계는
`${CLAUDE_PLUGIN_ROOT}/references/convention-precedence.md` 가 정한다. 여기 다시 적지 않는다.

## 제목은 "코드 변경" 이 아니라 "기능/동작 변경"

코드의 어디를 어떻게 고쳤는지는 diff 가 이미 준다.
제목에는 **사용자·시스템 관점에서 무엇이 달라졌는지** 적는다.

- ✅ `fix(auth): 토큰 만료 시 재로그인 없이 자동 갱신`
- ✅ `fix(cart): refresh the total as soon as quantity changes` — 언어는 저장소를 따른다
- ❌ `fix(auth): useSession 훅에서 token null 처리 추가`

**예외는 동작이 하나도 안 바뀌는 커밋뿐** — 이름변경·파일이동·포맷·dead code 제거.
이때만 코드 변경 자체를 제목으로 쓴다 (`refactor(store): persist 대상에서 임시 캐시 제거`).

**`refactor` 라는 type 은 면제가 아니다.** 인증 방식·아키텍처·보안·데이터 흐름이 바뀌면
동작·결과 관점으로 적는다 — ✅ `refactor(auth): API 요청 인증을 쿠키 자동 전송 방식으로 전환`
/ ❌ `refactor(auth): authApiClient 에서 Authorization 헤더 제거`

### 제목이 diff 와 맞나 (쓰고 나서 센다)

**제목은 diff 를 줄인 것이 아니라 주장이다.** 어긋나면 `git log` 를 훑는 사람이 커밋을 잘못 짚는다.

| 검사 | 걸리면 |
|---|---|
| 제목이 `추가`·`신설`·`도입` 인데 diff 가 삭제만 | 제목이 틀렸거나 커밋이 잘못 쪼개졌다 |
| 제목이 가리키는 파일이 diff 에 없음 | 같음 |
| 제목이 한 가지를 말하는데 diff 가 여러 파일·여러 주제 | 커밋을 쪼갠다 |

실제로 "섹션 정의와 상한 추가" 라는 제목에 **삭제 18줄만** 든 커밋이 나온 적이 있다.
앞 커밋이 파일을 훼손하고 뒤 커밋이 그걸 지운 것이라, 둘 다 제목과 어긋나 있었다.

## 본문 (권장, 강제 아님)

**diff 를 옮겨 적지 않는다.** 파일 목록과 바뀐 줄은 `git show --stat` 과 diff 가 이미 준다.
본문은 그 diff 를 다 읽을 수 없는 사람이 **의도를 잡는 자리**다.

필요할 때만 다음 섹션 가볍게 (제목과 같은 언어로):

- `요약` — **왜**, 버린 선택이 있으면 **어떻게**까지 (1~2줄, 불릿 아님)
- `영향` — 이 커밋으로 생길 수 있는 사이드이펙트와 동작 방식 변경
- `검증` — 실행한 확인 (`npx tsc --noEmit`, `npm run lint` 등)

**`영향` 에 무엇을 했는지 적지 않는다.** 그건 제목 몫이다. `영향` 은 **읽는 사람이 겪을 일**만
적는다 — 호출부가 깨지는지, 기존 동작이 달라지는지, 따라 손볼 것이 생기는지. 없으면 란을 뺀다.

**란 없는 문단을 본문 첫머리에 두지 않는다.** 할 말은 `요약` 란 안에 있다. 란 밖에 한 단락을
더 두면 같은 말을 두 번 하게 된다.

### `요약` 은 왜 — 무엇을 바꿨나는 제목이 갖는다

축은 둘뿐이고 둘째는 조건부다. 기본은 **한 줄**이다.

| 축 | 적는 것 |
|---|---|
| 왜 | 손대기 전 무엇이 문제였나 |
| 어떻게 (조건부) | 어떤 방식으로 — **버린 선택이 있을 때만** |

```
제목 : refactor: 작업 단위 개념어를 K 에서 Step 으로 대체

요약
Step · 작업 항목 · K 셋이 한 개념을 가리켜 문서마다 다르게 읽혔다.
별칭은 안 남겼다 — 남기면 이름이 갈라진 채 유지된다.
```

- **무엇을 바꿨는지 여기 안 적는다** — 제목의 자리다(`## 제목은 "코드 변경" 이 아니라 "기능/동작 변경"`). 적으면 제목 재진술 한 줄이 는다
- **결과도 안 적는다** — `영향` 란이 맡는다. 두 란이 같은 말을 하게 된다
- **바꾼 파일·줄 수를 나열하지 않는다** — `git show --stat` 이 준다
- **본문에서 이 란만 문단이다** — 나머지 란은 불릿 그대로

**세는 법 (쓰고 나서 대조한다)** — `요약` 의 각 줄을 제목 옆에 놓고 같은 뜻인 줄을 지운다.
지우고 남는 줄이 요약이다. 남는 게 없으면 **란째로 뺀다** — 제목이 이미 다 말한 커밋이다.

### 분량과 문체

**`요약` 은 2줄까지, 나머지 란은 3불릿까지. 본문 전체 12줄 이내.** diff 에 없는 것은 무한하다 —
포함 기준만 두고 분량 기준을 안 두면 계속 늘어난다.

**문체는 `writing-style.md` 를 따른다** — 불릿 종결·한 줄 한 문장·`키워드 : 설명` 꼴·인과 표시,
그리고 각 규칙을 **어겼는지 보는 법**이 거기 있다. 여기 사본을 두지 않는다.
**단 `요약` 란은 문단이라 불릿 종결 규칙이 안 걸린다** — 나머지 란에만 건다.

trivial 한 변경은 subject 만으로 충분, body 강요하지 말 것.
