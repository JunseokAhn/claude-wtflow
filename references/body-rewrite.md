# 이슈·MR 본문 재작성 규율

이미 올라간 **이슈 본문·MR 본문을 다시 쓰는 호출**에 걸리는 규칙. 훅(`hooks/guard-body-edit.sh`)과
짝이라 저장소 컨벤션이 덮지 않는다 — `convention-precedence.md` 의 대상이 아니다.
**`issue`·`mr`·`commit` 이 본문을 쓰기 전에 읽는다.**

무엇을 세어 미리보기에 낼지는 컨벤션 몫이다 — 이슈는 `issue-convention.md` 의
`## 확인 절차`, MR 은 `pr-convention.md` 의 `## 셀 수 있는 상한` 을 본다.

## 본문을 바꾸는 경로는 스킬 하나씩뿐이다

| 무엇 | 유일한 경로 | 예외 |
|---|---|---|
| 이슈 본문 | `/wtflow:issue --rewrite <N>` | `wtflow:commit` 의 체크박스 동기화 (`- [ ]` 한 줄만) |
| MR·PR 본문 | `/wtflow:mr --rewrite` | 없음 |

`gh issue edit --body` · `glab issue update -d` · `glab mr update -d` 를 직접 부르지 않는다.
**API 로 내려가도 마찬가지다** — `gh api --method PATCH … -f body=` 같은 형태는 훅이 잡지 못하지만,
훅이 막지 않는다는 것이 계약을 안 타도 된다는 뜻이 아니다.

**Why:** 재작성에는 템플릿 준수·미리보기·확인 계약이 걸려야 하는데, 수정 명령 직접 호출은
그걸 전부 건너뛴다. 경로를 하나로 두어야 그 계약이 실제로 걸린다.

## 읽지 않고 쓰지 않는다

본문 쓰기는 어느 호스트든 **전체 치환**이다. 현재 본문을 먼저 조회하지 않고 쓰면 그 순간 원문이 사라진다.

- 조회 명령과 본문 필드 이름은 `host-adapter.md` 의 `## 이슈 명령 대응` 에서 꺼낸다 —
  GitHub 은 `body`, GitLab 은 `description` 이라 이름째로 다르다
- 현재 본문을 못 읽으면 **중단한다.** 기억·대화 맥락으로 본문을 복원해 쓰지 않는다

## 본문은 파일로 넘긴다

줄바꿈·백틱·따옴표가 인자에서 깨진다. 인자에 직접 이어붙이지 않는다.

```
gh   issue edit   <N> --body-file <본문파일>       # GitHub — MR 은 gh pr edit
glab issue update <N> -d "$(cat <본문파일>)"       # GitLab — MR 은 glab mr update
```

`gh` 에는 파일 옵션이 있고(`--body-file`, 단축 `-F`) `glab` 에는 없어 `-d "$(cat …)"` 로 넘긴다.

## `WTFLOW_BODY_REWRITE=1` 을 빼지 않는다

본문을 고치는 호출은 훅이 막는다. 이 환경변수가 **"계약을 다 탄 재작성" 임을 밝히는 유일한 수단**이다
— 훅은 명령 문자열만 보므로 스킬 경유 여부를 스스로 알 수 없다. 호스트를 갈아끼워도 그대로 붙인다.

```
WTFLOW_BODY_REWRITE=1 gh issue edit <N> --body-file <본문파일>
```

- ⚠️ **이 환경변수를 붙인 호출은 조회·미리보기·확인을 실제로 거친 뒤여야 한다.** 건너뛰고 붙이면
  예외가 그대로 우회로가 된다
- 훅이 막았다는 응답을 받으면 **환경변수 누락을 먼저 의심한다.** 훅을 끄거나 우회하지 않는다
- 체크박스 동기화의 환경변수는 이름이 다르다(`WTFLOW_CHECKBOX_SYNC=1`) — 그 호출은 본문을
  다시 쓰는 게 아니라 `- [ ]` 한 줄을 켜는 것이라, 같은 호출에 본문 손질을 얹지 않는다

## 미리보기에는 셀 수 있는 변화를 낸다

"간결하게" 는 검사할 수 없지만 **바뀐 양**은 셀 수 있다. 확인은 산문 나열이 아니라
`AskUserQuestion` 이고, 질문 축은 생성 때와 달리 **"본문 이대로 반영할지"** 다.

- **템플릿에 없는 섹션이 1개라도 생기면 그 사실만으로 되묻는다** — 지어낸 섹션이 소리 없이
  들어가는 것이 실제로 일어난 사고다
- 줄이 늘면 **늘어난 분량이 무엇인지 한 줄로 적는다.** 그게 컨벤션이 금지한 것(근본원인 분석·
  코드 경로·세부 작업분해)이면 **묻지 말고 다시 쓴다** — 물어서 통과시킬 대상이 아니다
- 상한을 넘었거나 헤더가 템플릿과 어긋났을 때도 마찬가지로 **묻지 말고 다시 쓴다**
- 관측되지 않은 사실로 섹션을 채우지 않는다. 사례·수치를 지어내느니 그 섹션을 비워 둔다

### 바뀌는 줄은 diff 로 원문을 보인다

**개수는 얼마나 바뀌는지만 알려주고 무엇이 들어가는지는 안 알려준다.** 개수 표와 함께
현재 본문과 새 본문의 차이를 ` ```diff ` 블록으로 응답에 적는다.

| 줄 | 형태 |
|---|---|
| 지워지는 줄 | `-` 로 시작 |
| 더해지는 줄 | `+` 로 시작 |
| 문맥 | 바뀐 자리가 속한 섹션 헤더 한 줄. 앞에 공백 |

- **셸 출력에만 두지 않는다** — 도구 결과는 화면에서 접혀 ctrl+o 를 눌러야 보인다
- 줄 수를 줄이려고 원문을 요약하지 않는다. 바뀌는 줄이 길어도 그대로 적는다
- 응답 안 어디에 두는지는 `learning-implementation.md` 의 §1 예측 `### 어디에 두나` 가 정한다 — 여기 사본을 두지 않는다

**Why:** 완료 조건을 더하는 재작성에서 확인 화면에 「완료 조건 4줄 추가」 같은 개수만 나왔다.
새 본문은 접힌 셸 출력 안에만 있어 사용자가 무엇이 들어가는지 모른 채 「반영」을 고르게 됐다(#48).
이슈 생성 때는 본문을 응답에 적어 이 일이 없었다.
