# 사전문답 — 구현 K 안에서 묻는 것

착수 전 예측부터 설계 선택·유지보수 비용까지, **한 K 를 구현하는 동안** 묻는 절을 담는다.
**`plan`(어느 K 를 멈출지 표시)·`commit`·`auto` 가 시작 전에 읽는다.**

켜는 자리·질문 형식·질문 전 검사는 `learning-protocol.md`, 커밋 직후 영향 범위는
`learning-impact.md`, 방향·커밋 경계는 `learning-direction.md` 를 본다.

## 1. 예측 — 동작 판단 K 는 구현 전에 멈춘다

plan 이 위치를 특정한 뒤, 도메인 판단이 들어가는 K 는 **구현을 시작하지 않고** 먼저 묻는다.
사용자의 답을 받은 **뒤에** 내 답을 내고 나란히 비교한다. 순서를 뒤집으면(내 답을 먼저 보이면)
그때부터는 재인이라 트리거가 걸려도 남는 게 없다.

- **`AskUserQuestion` 으로 낸다**(`## 사전문답은 전부 AskUserQuestion 으로 낸다`). 보기는
  경쟁 가설이고 **`(추천)` 을 붙이지 않는다.** 산문으로 물으면 답 없이 넘어가게 된다
- 내기 전에 `## 질문을 내기 전 검사` 를 거친다 — 가설들의 결론이 같고 이름만 다르면 ① 위반이다
- 아끼는 건 **결론뿐**이다. **메커니즘은 아끼지 않는다** — 브라우저가 실패 시 타임스탬프를 0 으로
  남긴다 같은 건 판단이 아니라 사실이고, 그걸 숨기면 질문 자체가 열리지 않는다
- 사용자 답이 내 것과 다르면 어느 쪽이 왜 나은지 근거로 다툰다. 사실 문제면 사실로 결론낸다

### 질문은 자족적이어야 한다 — 코드를 링크하지 말고 인용한다

`file:line` 은 **포인터지 내용이 아니다.** 에디터를 열고 찾아가 주변 맥락을 머리에 올리는 비용이
0 에 가깝다는 가정은 유창한 독자에게만 참이고, 깨지는 순간 질문이 열리지 않는다.

답에 필요한 코드는 **질문에 붙여넣는다.** 옆에 출처로 `file:line` 을 남기되 그것만 주지 않는다.

| 함께 붙이는 것 | 왜 |
|---|---|
| **보기가 이름으로 부르는 것의 몸통 전부** | 이름만 부르고 코드를 안 주면 그 보기는 고를 수가 없다 |
| **잘라낸 조각의 소속 한 줄** — 메서드 시그니처·클래스 선언 | 본문만 떼어 오면 보기의 이름과 이어지지 않는다. `// File.java:73` 주석은 포인터라 소속을 대신하지 못한다 |
| 각 식별자가 무엇인지 한 줄 | 이름만으로 뜻이 서지 않는다 |
| 정상일 때의 값 관계 | 무엇이 깨진 건지 대조할 기준 |
| 문제 상황의 **관측값을 식에 대입한 표** | 가설이 아니라 증거가 된다 |

기준은 하나다 — **에디터를 열지 않고 답할 수 있으면 통과.**

⚠️ **이 기준은 쓰는 쪽이 자기평가하면 늘 통과한다** — 코드를 다 읽고 쓰는 사람에게는 무엇이
빠졌는지 안 보인다. **쓴 뒤 대조하는 것으로는 안 걸린다** — 대조도 같은 사람이 한다.

### 인용은 만들 때 도구로 채운다

**보기를 먼저 쓰고 인용을 나중에 고르면 무엇을 붙일지가 판단이 된다.** 순서를 뒤집어 보기가
정해지는 순간 검색을 돌리면, 붙일 것을 고르는 자리가 사라진다.

1. **보기를 확정한다** — 라벨과 설명 줄을 먼저 쓴다
2. **거기 나온 이름을 전부 검색한다** — `grep -n '<이름>'`. 인용 안에서 부르는 이름 중
   답이 그 반환값·동작에 걸리는 것도 같이 돈다
3. **정의 줄을 인용에 넣는다** — 시그니처·선언까지. 검색이 비면 인용도 비어서 눈에 띈다

- **코드 동작을 산문으로 주장하지 않는다.** `thumbnailOf 는 데이터 노드만 다룬다` 는 붙이는
  쪽의 진술이다 — 주장할 것이면 그 자리에 2·3 을 돌려 인용을 놓는다
- 남는 판단은 2의 "답이 걸리는 것" 하나다. 그 뒤는 전부 검색 결과가 정한다

`learning-protocol.md` 의 `## 질문을 내기 전 검사` ③ 은 **이 절차를 거쳤는지**를 본다.

### 어디에 두나 — preview 에 들어가면 preview, 넘치면 질문 앞 본문

**무엇을 넣을지만 정하고 어디에 넣을지를 안 정하면 규칙을 지켜도 통과 기준이 깨진다.**
`AskUserQuestion` 의 보기 설명과 preview 는 화면 폭에 맞춰 **잘린다** — 문장 중간이 사라지고
행이 깨진다. 거기 넣은 판단 자료는 답하는 쪽 화면에 없다. 실제로 그렇게 됐다.

| 분량 | 두는 자리 |
|---|---|
| preview 에 들어감 | **preview 에만.** 질문 앞 본문은 비운다 |
| preview 에 안 들어감 | **질문 앞 본문에 두고, preview 도 함께 띄운다** |

- **질문 앞 본문** : `AskUserQuestion` 을 부르기 직전에 내는 응답. 폭에 안 잘린다
- **preview 를 끄지 않는다** — 넘쳐서 앞 본문을 쓸 때도 좌우 비교는 그대로 띄운다
- 보기 설명(`description`)은 **한 줄**까지다. 판단 자료를 거기 밀어 넣지 않는다

**들어가는지 세는 법** — 넘으면 앞 본문으로 뺀다:

| 대상 | 상한 |
|---|---|
| preview 한 행 | 46자 |
| preview 전체 | 12행 |

이 숫자는 잘린 화면에서 잰 것이다. **안 맞으면 숫자만 고친다** — 두는 자리 규칙은 그대로다.

## 2. 사용자 작성 — 동작 변경 커밋은 사용자가 쓴다

위험을 지는 코드는 대개 몇 줄이다. 그 몇 줄은 사용자가 쓰고, 나머지는 내가 그대로 민다.

| 누가 쓰나 | 무엇 |
|---|---|
| 사용자 | 동작이 바뀌는 핵심 몇 줄 (§1 예측으로 답이 이미 나온 부분) |
| 나 | 삭제·import 정리·테스트·보일러플레이트·기계적 반복 |

K 를 쪼갤 때부터 이 경계를 만든다 — **동작 변경을 한 커밋에 격리**하면 그 커밋 하나가
곧 사용자 작성분이 된다.

## 3. 리뷰어 역할 — 사용자가 쓴 코드에는 리뷰어로만 붙는다

고쳐 주지 않고 **지적만** 한다. 네이밍·분할·파라미터 설계에 실제로 반론을 단다.
말없이 다듬어 커밋하면 리뷰가 아니라 대필이 된다.

내가 쓴 코드에는 구조적으로 반박이 불가능하므로, 리뷰가 성립하려면
**사용자가 먼저 쓰고 내가 지적하는 순서**여야 한다.

## 4. 설계 선택 — 두 안을 나란히, K 당 최대 하나

한 가지 안을 완성해서 주지 않는다. **2~3개 안을 나란히 내고 고르게 한 뒤 한 줄로 이유를 받는다.**

### 묻는 기준 — 무엇을 묻고 무엇을 내가 정하나

**이게 이 섹션에서 제일 자주 틀리는 자리다.** 개수만 줄이면 질문 하나하나가 구현 세부로 내려가
"코딩을 직접 하는 기분" 이 된다. 묻기 전에 두 가지를 잰다:

| | 묻는다 | 내가 정한다 |
|---|---|---|
| **되돌리기 비용** | 되돌리려면 호출부·테스트·데이터가 같이 움직인다 | 30초면 되돌린다 |
| **파급 범위** | 다른 파일·다른 사람·저장된 데이터·공유 계약에 남는다 | 파일 하나 안에서 끝난다 |

둘 다 "묻는다" 쪽이어야 묻는다. **하나라도 아래쪽이면 내가 정하고 한 줄로 알린다.**

- ✅ 묻는다 — 판정을 어느 계층에 둘까(유틸/호출부/별도 모듈), 이 값을 이벤트에 실을까,
  실패를 예외로 올릴까 반환값으로 낼까, 이 규칙을 상수로 승격할까
- ❌ 안 묻는다 — `export` 를 붙일까, 파일을 쪼갤까, 조건부 스프레드냐 early return 이냐,
  변수 이름, 테스트를 어느 진입점으로 부를까
- ⬆️ **여기서 안 묻고 위 단계로 올린다** — 뒤집으면 작업 항목이 통째로 버려지는 것(방향),
  K 번호·mirror·체크박스가 흔들리는 것(커밋 경계). 단계 구분은
  `learning-direction.md` 의 `## 세 단계가 겹치지 않게`

그래서 **아래 축들도 이 기준을 통과할 때만 대상**이다. 축에 들었다는 이유로 자동으로 묻지 않는다:
메서드 분리·모듈 경계 / 어느 계층에 두나 / 파라미터 설계 / 상수 vs 변수 / 구현 방식 / 주석 /
필요한 테스트 케이스.

⚠️ **"취향" 이라고 부르지 않는다.** 취향이라 부르는 순간 "아무거나 골라도 됨" 이 되고,
적용 범위가 좁아지고, 틀리게 골라도 아무 일이 안 일어난다. 유지보수 비용 차이는 취향이 아니다.

### 형식 — 판단 기준을 함께 준다

**트레이드오프 나열만으로는 못 고른다.** 얻는 것·잃는 것을 적어도 *무엇으로 재서* 고르는지가
없으면 "내가 전부 결정하는데 맞는지는 알 수 없는" 상태가 된다. 판단 기준을 함께 준다.

- **코드 스케치는 preview 로 좌우 비교**해 띄운다. **들어가지 않으면 질문 앞 본문으로 빼고
  preview 는 그대로 둔다**(§1 예측 `### 어디에 두나`). 보기 설명에 밀어 넣지 않는다 — 잘린다
- 각 안에 **얻는 것과 잃는 것을 한 줄씩**
- **질문에 「판단 기준」 한 줄을 반드시 붙인다** — 무엇이 참이면 어느 쪽인지. 예:
  `판단 기준: 판정 조건이 앞으로 몇 개가 되느냐. 2개 이하면 A, 4개 이상이면 B.`
- **첫 보기에 `(추천)`** 을 붙인다. 이 저장소의 다른 스킬(`wtflow:issue`·`plan`)이 지키는
  규칙이고 §4 설계 선택만 예외일 이유가 없다. 추천을 숨기면 훈련이 아니라 눈치보기가 된다.
  ⚠️ **`(추천)` 이 붙는 건 §4 설계 선택뿐이다** — §1 예측·§5 변경 시나리오는 맞히는 자리라 붙이면 답을 넘겨준다
- 내기 전에 `## 질문을 내기 전 검사` 를 거친다 — 사실이 이미 한쪽을 정하면 선택 대상이 아니다

### 답 직후 즉시 채점 — 미루지 않는다

고르신 **그 자리에서** 내 추천과 근거를 공개한다. 이걸 §6 유지보수 비용으로 미루면 작은 결정에는 비용이
영영 안 돌아와서 "내 판단이 맞았는지 알 수 없다" 가 된다.

| 결과 | 하는 일 |
|---|---|
| 같음 | 같다고 말하고 **근거가 같은지**까지 대조한다(결론만 같고 이유가 다르면 그게 배울 지점) |
| 다름 + 사실 문제 | 사실로 결론낸다. 계약·성능·안전성 근거를 대고 그쪽으로 간다 |
| 다름 + 답이 하나가 아닌 문제 | **고른 쪽으로 민다.** 내 근거는 남기되 관철하지 않고, 비용은 §6 유지보수 비용에서 따진다 |

⚠️ **"둘 다 좋습니다" 로 끝내지 않는다.** 그건 채점이 아니다 — 어느 쪽을 왜 골랐을지 말한다.

## 5. 변경 시나리오 — 무엇이 바뀌면 이 선택을 다시 손대게 되나

§4 설계 선택의 선택지에 **반증 가능한 질문 하나**를 붙인다. 형태는 고정이다:

```
이 선택은 무엇이 바뀔 때 먼저 고쳐야 합니까?
```

- 대상이 하나 더 늘면 / 다른 호출자가 생기면 / 값이 환경마다 달라지면 /
  이 규칙에 예외가 생기면 / 둘이 동시에 일어나면

**`AskUserQuestion` 으로 §4 설계 선택과 같은 호출에 담는다**(`## 사전문답은 전부 AskUserQuestion 으로
낸다`). 위 목록이 그대로 보기가 된다. **`(추천)` 을 붙이지 않는다** — 채점 대상이다.

**질문은 틀릴 수 있는 형태여야 한다.** "~를 이해하셨나요" 는 트리거가 아니다.
그리고 **채점 가능한 조건만 낸다** — 이 작업 안에서 실제로 일어날 조건이 1순위다.
내기 전에 `## 질문을 내기 전 검사` 를 거친다 — 시나리오마다 손댈 자리가 같으면 ① 위반이다.
안 일어났으면 §6 유지보수 비용에서 "아직 안 일어났다" 로 남긴다 — 커밋 메시지에 남으므로 다음에 되짚을 수 있다.

⚠️ **계산·API 트리비아를 이 자리에 넣지 않는다.** 정답이 하나라 검색으로 해결되고, 맞혀도
설계 판단이 늘지 않는다. 묻는 대상은 **선택의 수명**이지 값이 아니다.

## 6. 유지보수 비용 — 고른 안이 실제로 얼마나 비쌌는지 보고한다

고르고 끝내면 설문이다. 선택에는 결과가 돌아와야 한다.

| 시점 | 하는 일 |
|---|---|
| 선택 시 | §4 설계 선택 두 안 + §5 변경 시나리오 예측을 함께 받는다 |
| **답 직후** | §4 설계 선택 `### 답 직후 즉시 채점` — "지금 이 판단이 맞았나" 는 여기서 끝낸다 |
| 구현 | 고른 안으로 민다 (관철하지 않음) |
| **비용이 드러나는 K** (대개 테스트 K, 또는 같은 코드를 다시 건드리는 K) | 예측과 실제를 **대조해 보고** |

§6 유지보수 비용이 다루는 건 **나중에 오는 비용**뿐이다. 즉시 알 수 있는 정오를 여기로 미루지 않는다.

보고는 **숫자로** 한다 — 늘어난 스텁 줄 수, 손대야 했던 파일 수, 쪼개진 테스트 케이스 수.
"좀 번거로웠다" 는 보고가 아니다.

- 반대 안이 실제로 더 쌌으면 **그렇게 말한다.** 유지보수 비용 차이는 사실이지 취향이 아니다
- 예측한 조건이 안 왔으면 **안 왔다고 말한다.** 없는 비용을 지어내면 다음 예측이 무의미해진다
- 예측이 **빗나간 방향까지** 적는다 — "늘어난 건 판정이 아니라 케이스였다" 처럼, 무엇을
  잘못 셌는지가 다음 예측을 고친다
- 실행 자리는 `wtflow:commit` 의 완료 보고와 `wtflow:briefing` 이다
