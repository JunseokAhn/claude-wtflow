# 이슈 컨벤션

> **이 문서는 탐색 순서의 마지막 층(플러그인 기본값)이다.** 저장소 `.wtflow/` 나
> `~/.claude/wtflow/` 에 같은 이름의 파일이 있으면 그쪽 `##` 절이 이긴다 — `${CLAUDE_PLUGIN_ROOT}/references/convention-lookup.md`.

이슈의 제목·라벨·본문 형식과 사용자 확인 절차. **`/wtflow:issue` 가 시작 전에 읽는다.**

커밋 메시지 형식은 `commit-convention.md`, 브랜치 이름·K 모델·note 계층은
`worktree-discipline.md` 를 본다.

이 문서는 **저장소가 통째로 갈아끼울 수 있는 규칙**이다. 반대로 이슈를 만드는 절차 자체
(prefix 추정 → 라벨 → 제목 → 본문 → 확인 → 생성 → note)는 스킬의 계약이라 여기 없다.

## 라벨 인벤토리

**여기 있는 값만 쓰고 없는 라벨을 만들지 않는다** — 의심되면 `glab label list -R <repo>` 로 검증한다.
세 축을 모두 붙인다.

| 축 | 값 | 추정 어려울 때 |
|---|---|---|
| **종류** (필수) | `종류:기능` · `종류:리팩터링` · `종류:버그` · `종류:인프라` | 아래 prefix 매핑이 자동 결정 |
| **난이도** | `난이도:낮음` · `난이도:보통` · `난이도:높음` | `난이도:보통` (※ 쉬움/어려움 아님 — 낮음/높음) |
| **우선순위** | `우선순위:낮음` · `우선순위:보통` · `우선순위:높음` · `우선순위:긴급` | `우선순위:보통` |

## prefix → 라벨 매핑

| prefix | 종류 라벨 |
|---|---|
| `fix:` | `종류:버그` |
| `feat:` | `종류:기능` |
| `refactor:` | `종류:리팩터링` |
| `chore:` | `종류:인프라` |
| `docs:` · `test:` · `perf:` · `style:` | 전용 종류가 없다 → `종류:인프라`(일반 버킷)로 두되 확인 단계에서 조정 |

## 제목 규칙

`<prefix> <한국어 한 줄 요약>` — scope 를 붙여 `<prefix>(<scope>): …` 로 써도 된다.

- **명사구로 끝낸다** (`…추가` · `…제거` · `…전환` · `…정리` · `…방지` · `…누락`).
  **서술형 종결 금지** — `~한다` · `~하도록 함` · `~옮김` · `~막음`
- **두 산출물이면 접속사 말고 `+`** — ✅ `feat(search): 이미지 검색 API 추가 + 결과 화면 연동` /
  ❌ `feat(search): 검색 API 를 만들고 화면에 연동한다`
- **보충은 괄호 하나까지** — `fix(upload): 동시 요청 시 파일명 중복 방지 (유니크 인덱스)`
- **식별자·영어는 원문 유지** — 코드에 있는 이름(상수·함수·API·설정 키)은 그대로 쓴다.
  억지로 한글화하면 검색이 안 된다
- 예: `fix: 사용자 로그인 시 토큰 만료 에러` ·
  `refactor(auth): 세션 저장소를 서버 측 만료 방식으로 이관`
- **커밋 제목과 같은 규칙이다** — `commit-convention.md` 의 `## Subject` 를 이슈 제목에도 그대로
  적용한다(한쪽만 고치면 갈린다)

## 본문 작성 규칙

저장소 이슈 템플릿을 우선 사용한다(아래 `## 본문 템플릿`). 템플릿이 없으면 한 줄 요약.

- **이슈는 "무엇/왜"의 짧은 메모다.** 근본원인 분석·코드경로·클래스명 나열·해결책 설계·세부
  작업분해는 이슈에 쓰지 않는다 — 그건 이후 `/wtflow:plan` plan 단계 몫이다. 지금 이슈에 결론을
  박으면 plan 과 중복되거나 어긋난다
- **서술 절은 목록이 기본** — `배경`·`현상`·`목적`·`요약`·`상세 설명`처럼 사실을 늘어놓는 절은
  문단 대신 목록으로 쓴다. **한 줄에 한 사실.** 두 문장으로 끝나는 이슈는 문단도 된다. 다만
  **세 문장을 넘기는 순간 목록으로 바꾼다** — 문단이 길어지면 훑어서 요점을 집을 수 없다
  - `작업 항목` 체크리스트는 이 규칙과 무관하다 — 그 형태는 진행 상태를 읽는 쪽이 의존하므로
    손대지 않는다 (`- [ ] <번호>. `)
  - 같은 취지의 규칙이 이미 `/wtflow:milestone` 에 있다. 이 줄은 그걸 **이슈 본문까지 넓힌 것**이고,
    어휘를 새로 만들지 않는다
- **이미 상세히 계획해둔 게 있으면 이슈에 밀어넣지 말고 note 로 흘려보낸다.** 페이로드 계약·타입·
  에러코드·호출 순서 같은 것이 여기 해당한다. 여러 이슈·레포가 공유해야 하는 계약이라면
  `/wtflow:milestone` 의 마일스톤 note 가 목적지다
- ⚠️ **이슈는 자족적이어야 한다 — wtflow 를 전혀 모르는 글로 쓴다.** 팀원에겐 `~/.claude/notes/` 가
  없다. **어느 섹션에도**(`참고 자료` 포함 — 여기가 제일 잘 샌다) 쓰지 않는다: note 의
  **절 이름 참조**(~~"계약 상세는 마일스톤 문서 … 절 참조"~~), **로컬 경로·파일명**(`.claude/…`,
  "마일스톤 문서"), **내부 용어**(K 번호·mirror 분기·accumulator·워크트리).
  맥락이 더 필요하면 가리키지 말고 **그 내용을 직접 풀어 쓴다.** `참고 자료` 에는 팀원이 실제로
  열 수 있는 것만(GitLab 링크·외부 URL·Notion)

## 본문 템플릿

1. **템플릿 탐색 — 두 경로를 다 본다** (Glob). 한쪽만 보면 다른 호스트의 레포에서 템플릿이
   **있는데도** 없다고 판단해 절을 지어낸다(이게 가장 흔한 실패다):
   - `.gitlab/issue_templates/*.md`
   - `.github/ISSUE_TEMPLATE/*.md`

   둘 다 있으면 remote 호스트에 맞는 쪽(`github.com` → `.github/`), 호스트를 못 가리면 `.github/`
2. **prefix → 템플릿 매핑** (있는 것만 적용):
   - `fix:` → `bug.md`
   - `feat:` → `feature.md`
   - `refactor:` → `feature.md` (작업 항목 구조가 적합)
   - `chore:` → `infra.md` (배포·환경·인프라 변경이 다수)
   - `docs:` → `docs.md`
   - `test:` → 템플릿 없이 한 줄 요약
3. **템플릿 채우기** (간결성·헤더 고정 원칙):
   - 템플릿을 Read 해서 섹션 구조 파악. **GitHub 템플릿 머리의 YAML frontmatter(`name:`·`about:`·
     `labels:`)는 본문이 아니다** — 옮겨 적지 않는다. 절 구조는 그 아래 첫 `##` 헤더부터다
   - **헤더 고정**: 템플릿의 헤더를 그대로 쓴다. 추가·삭제·개명 금지 (`상세 설명`을 `배경`으로
     개명하거나 `해결 방향` 같은 새 헤더 추가 금지)
     - 예외는 **템플릿이 스스로 지워도 된다고 적어둔 절**뿐이다(예: `bug.md` 의 `환경` — "특정
       환경에서만 재현될 때만"). 지운 절을 나중에 되살리지도 않는다 — 되살리면 본문만 자란다
   - **간결성 상한**: 위 `## 본문 작성 규칙` 의 `서술 절은 목록이 기본` 을 따른다 — 여기 다시 적지
     않는다. 코드 경로/클래스명 나열, 근본원인 추론, 해결책 설계 금지
   - **작업 항목/작업 계획**: **큰 틀의 작업 단위**로 작성 (개수 고정 아님 — 작업 성격에 맞게, 보통
     2~5개). 세부 단위 분해는 plan 단계 몫. ⚠️ 이 작업 항목이 이후 `/wtflow:plan` plan·
     `/wtflow:commit` 의 **K 넘버링 기준**이 된다 (작업 항목 N = Step N = K N = mirror 분기 `-00N`).
     따라서 각 항목은 독립적으로 commit·검증 가능한 단위가 되도록 잡는다(순수 조사·식별·분석처럼
     산출물 커밋이 없는 단계는 항목이 아니라 plan 몫 — "제거 대상 식별" 같은 항목 금지). 큰 단위조차
     안 잡히면 placeholder 유지
     - **마크다운 체크박스 `- [ ]` 로, 위에서부터 K 순서(N=1,2,…)대로 한 줄씩** 작성(다른
       체크리스트와 섞지 않기) — K 완료 시 N번째 항목이 자동 체크되기 때문. 템플릿이 평문 나열이면
       체크박스로 바꿔 적는다
   - **환경**: 특정 환경에서만 발생하는 등 실제 신호가 있을 때만 채움. 코드 레벨 버그처럼 의미
     없으면 placeholder 유지 (`서버/브랜치: <서버> / develop` 같은 무의미한 boilerplate 금지)
   - 그 외 정보 부족한 섹션은 **placeholder 그대로 유지** (사용자가 GitLab UI 에서 보강)
   - HTML 주석 `<!-- ... -->` 도 그대로 유지 (작성 가이드)
4. **폴백**:
   - 두 디렉토리 모두 없음 → 한 줄 요약만
   - 매핑된 파일명 없음 (예: `bug.md` 가 `defect.md` 로 명명) → Glob 결과에서 prefix·종류와 유사한
     파일명 추정 (`bug|defect|fix` 등). 모호하면 사용자에게 묻기

## 확인 절차

### 생성

**산문 말고 `AskUserQuestion`.** 본문 미리보기를 보인 뒤, 조정 가능한 축(prefix/종류·난이도·
우선순위)을 `AskUserQuestion` 으로 묻는다(산문으로 "이대로 생성할까?" 나열 금지 — 이게 가장 흔한
누락). 각 보기 첫째에 추천안을 `(추천)` 으로 표기. 자유 입력 경로는 클라이언트가 자동으로 붙이는
"Other" 로 보장되므로 **"직접 입력" 보기를 따로 넣지 않는다**(여기 질문은 prefix·라벨처럼 보기가
유한해서 Other 한 줄이면 충분하다. 반대로 사용자가 **값을 지어내야 하는** 질문 — 페이로드 필드·
에러코드 같은 것 — 에는 `직접 입력` 보기를 넣는다). 답이 추천과 같으면 그대로, 다르면 반영해 생성.

### 재작성

**질문 축은 라벨·prefix 가 아니라 "본문 이대로 반영할지" 다.** 생성과 갈리는 유일한 지점이다.
`AskUserQuestion` 으로 묻는다(산문 나열 금지, 보기 첫째에 `(추천)`).

미리보기에는 **셀 수 있는 변화**를 함께 낸다 — "간결하게" 는 검사할 수 없지만 이건 셀 수 있다:

| 항목 | 형태 |
|---|---|
| 절 수 | `6개 → 6개` (안 바뀌면 `변화 없음`) |
| 줄 수 | `15줄 → 18줄 (+3)` — 목록·단계 줄 기준 |
| 템플릿에 없는 절 | 이름을 전부 나열. 없으면 `없음` |
| 지워지는 절 | 이름을 전부 나열. 없으면 `없음` |

- **템플릿에 없는 절이 1개라도 생기면 그 사실만으로 되묻는다** — 지어낸 절이 소리 없이 들어가는
  것이 실제로 일어난 사고다(템플릿 외 절 3개)
- 줄이 늘면 **늘어난 분량이 무엇인지 한 줄로 적는다**. 그게 `## 본문 작성 규칙` 이 금지한 것
  (근본원인 분석·코드 경로·세부 작업분해)이면 **묻지 말고 다시 쓴다** — 물어서 통과시킬 대상이 아니다
- 관측되지 않은 사실로 절을 채우지 않는다. 사례·수치를 지어내느니 그 절을 비워 둔다
