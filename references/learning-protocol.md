# 사전문답 규율

작업을 대신 해 주는 것과 **작업자가 그 코드를 계속 쥘 수 있게 하는 것**은 다른 목표다.
이 문서는 후자를 위해 K 착수 전후에 끼워 넣는 문답 장치를 담는다.
**`plan`·`commit` 이 시작 전에 읽고, `auto` 는 아래 `## 끄는 자리` 규칙에 따라 대부분 끈다.**

브랜치 이름·K 모델·note 계층은 `worktree-discipline.md`, 커밋 메시지 형식은
`commit-convention.md` 를 본다.

## 이 문서가 노리는 두 축

| 축 | 무엇 | 절 |
|---|---|---|
| **동작 판단** | 무엇이 문제고 무엇으로 바꿀 것인가 | §1 · §2 · §3 |
| **설계 판단** | 어떻게 짤 것인가 — 분리·파라미터·상수·위치·주석·테스트 | §4 · §5 · §6 |

⚠️ **정답이 하나인 것은 대상이 아니다.** 계산(`a - b` 가 얼마인가), API 트리비아
(`이 옵션을 빼면 기본값이 뭔가`)는 검색하면 나오고, 맞혀도 판단력이 늘지 않는다.
문답의 소재는 **답이 갈리고 대가가 따르는 것**뿐이다.

**Why (동작 축):** 완성된 diff 를 읽는 것은 재인(recognition)이라 거의 남지 않는다. 이해는
인출(recall)에서 붙으므로 브리핑 품질을 올리는 방향으로는 이 문제가 풀리지 않는다. 한편 커밋을
쪼개 보면 도메인 판단이 든 부분은 대개 몇 줄이고 나머지는 기계적이라, **작은 쪽만 사람이 쥐면
처리량 손실이 적다.**

**Why (설계 축):** 설계는 설명으로 옮겨지지 않고 **대가로만 학습된다.** 원래 그 대가는 자기 코드를
오래 유지보수하며 치른다 — 잘못 자른 경계, 잘못 뽑은 파라미터의 청구서가 몇 달 뒤 자기에게 온다.
코드를 위임하면 코드가 늘어나는 속도는 그대로인데 **청구서를 받는 사람이 사라진다.** 고르게만 하고
끝내는 것은 설문이지 훈련이 아니다. §6 은 그 청구서를 작업 안에서 인위적으로 되살린다.

## 켜는 자리 / 끄는 자리

| | 사전문답 |
|---|---|
| 배울 게 있는 이슈 (도메인 판단·설계 선택) | ✅ 켠다 |
| 구현 K 안에 **내가 임의로 정하고 넘어갈 뻔한 설계 선택**이 있음 | ✅ §4 — **K 당 하나** |
| 급한 작업 / 사용자가 "빨리" 를 명시 | ❌ 끈다 |
| `/wtflow:auto` 를 사용자가 직접 호출 | ❌ 사전 멈춤은 끈다 (§5·§6 은 사후로 미룸) |
| 삭제·import 정리·포맷·보일러플레이트 | ❌ 배울 게 없다 — 그냥 진행 |

⚠️ **K 당 5~15분이 늘어난다.** 마찰 관리는 **개수 상한**으로 한다 — 대상 범위를 좁히지 말고
K 당 §1 하나, §4 하나까지만. plan 이 K 를 낼 때 **어느 K 가 대상인지 먼저 표시**한다.

## 1. 예측 후 공개 — 동작 판단 K 는 구현 전에 멈춘다

plan 이 위치를 특정한 뒤, 도메인 판단이 들어가는 K 는 **구현을 시작하지 않고** 먼저 묻는다.
사용자의 답을 받은 **뒤에** 내 답을 내고 나란히 비교한다. 순서를 뒤집으면(내 답을 먼저 보이면)
그때부터는 재인이라 장치가 죽는다.

- 아끼는 건 **결론뿐**이다. **메커니즘은 아끼지 않는다** — 브라우저가 실패 시 타임스탬프를 0 으로
  남긴다 같은 건 판단이 아니라 사실이고, 그걸 숨기면 질문 자체가 열리지 않는다
- 사용자 답이 내 것과 다르면 어느 쪽이 왜 나은지 근거로 다툰다. 사실 문제면 사실로 결론낸다

### 질문은 자족적이어야 한다 — 코드를 링크하지 말고 인용한다

`file:line` 은 **포인터지 내용이 아니다.** 에디터를 열고 찾아가 주변 맥락을 머리에 올리는 비용이
0 에 가깝다는 가정은 유창한 독자에게만 참이고, 깨지는 순간 질문이 열리지 않는다.

답에 필요한 코드는 **질문 안에 붙여넣는다.** 옆에 출처로 `file:line` 을 남기되 그것만 주지 않는다.

| 함께 붙이는 것 | 왜 |
|---|---|
| 각 식별자가 무엇인지 한 줄 | 이름만으로 뜻이 서지 않는다 |
| 정상일 때의 값 관계 | 무엇이 깨진 건지 대조할 기준 |
| 문제 상황의 **관측값을 식에 대입한 표** | 가설이 아니라 증거가 된다 |

기준은 하나다 — **에디터를 열지 않고 답할 수 있으면 통과.**

## 2. 동작 변경 커밋은 사용자가 작성

위험을 지는 코드는 대개 몇 줄이다. 그 몇 줄은 사용자가 쓰고, 나머지는 내가 그대로 민다.

| 누가 쓰나 | 무엇 |
|---|---|
| 사용자 | 동작이 바뀌는 핵심 몇 줄 (§1 로 답이 이미 나온 부분) |
| 나 | 삭제·import 정리·테스트·보일러플레이트·기계적 반복 |

K 를 쪼갤 때부터 이 경계를 만든다 — **동작 변경을 한 커밋에 격리**하면 그 커밋 하나가
곧 사용자 작성분이 된다.

## 3. 사용자가 쓴 코드에는 리뷰어로만 붙는다

고쳐 주지 않고 **지적만** 한다. 네이밍·분할·파라미터 설계에 실제로 반론을 단다.
말없이 다듬어 커밋하면 리뷰가 아니라 대필이 된다.

내가 쓴 코드에는 구조적으로 반박이 불가능하므로, 리뷰가 성립하려면
**사용자가 먼저 쓰고 내가 지적하는 순서**여야 한다.

## 4. 설계 선택은 두 안을 나란히 — K 당 하나

한 가지 안을 완성해서 주지 않는다. **2~3개 안을 나란히 내고 고르게 한 뒤 한 줄로 이유를 받는다.**

### 대상 — "내가 임의로 정하고 넘어갈 뻔한 선택"

"진짜로 갈리는 판단만" 이 아니다. 그렇게 좁히면 훈련하려던 것이 전부 빠진다.
아래는 전부 대상이다:

| 축 | 갈리는 예 |
|---|---|
| 메서드 분리·모듈 경계 | 한 함수가 읽기+판정을 다 하나, 판정을 뽑아내나 |
| 어느 층에 두나 | 유틸 안 / 호출부 / 별도 파일 |
| 파라미터 설계 | 인자 나열 / 객체 / 함수 주입 |
| 상수 vs 변수 | 인라인 리터럴 / 이름 붙인 상수 / 설정값으로 승격 |
| 구현 방식 | 조건부 스프레드 / 만든 뒤 삭제 / 검증 후 early return |
| 주석 | 무엇을 남기고 무엇을 코드로 드러내나 |
| 테스트 | 무엇이 **필요한** 케이스인가, 무엇이 테스트하기 좋은 모양인가 |

⚠️ **"취향" 이라고 부르지 않는다.** 취향이라 부르는 순간 "아무거나 골라도 됨" 이 되고,
적용 범위가 좁아지고, 틀리게 골라도 아무 일이 안 일어난다. 유지보수 비용 차이는 취향이 아니다.

### 형식

- **`AskUserQuestion` 의 preview 로 코드 스케치를 좌우 비교**로 띄운다. 본문 텍스트로 길게 쓰면
  안 읽힌다 — 본문엔 **선택지 이름과 한 줄 차이만** 남긴다
- 각 안에 **얻는 것과 잃는 것을 한 줄씩.** 장점만 적으면 고를 근거가 없어 결국 첫 보기를 찍는다
- 고른 쪽이 내 판단과 달라도 **그대로 민다.** 관철하지 않는다 — 대신 §6 에서 청구서를 낸다
- 동작·성능·안전성에 실제 차이가 있으면 선택 대상이 아니다. 사실로 알리고 그 근거로 정한다

## 5. 변경 압력 예측 — 고르기 전에 "무엇이 무너지나" 를 받는다

§4 의 선택지에 **반증 가능한 질문 하나**를 붙인다. 형태는 고정이다:

```
이 선택은 무엇이 바뀔 때 먼저 무너집니까?
```

- 대상이 하나 더 늘면 / 다른 호출자가 생기면 / 값이 환경마다 달라지면 /
  이 규칙에 예외가 생기면 / 둘이 동시에 일어나면

**질문은 틀릴 수 있는 형태여야 한다.** "~를 이해하셨나요" 는 장치가 아니다.
그리고 **채점 가능한 압력만 낸다** — 이 작업 안에서 실제로 도착할 압력이 1순위다.
도착하지 않으면 §6 에서 "아직 안 왔다" 로 남기고 note 에 적어 다음에 되짚는다.

⚠️ **계산·API 트리비아를 이 자리에 넣지 않는다.** 정답이 하나라 검색으로 해결되고, 맞혀도
설계 판단이 늘지 않는다. 묻는 대상은 **선택의 수명**이지 값이 아니다.

## 6. 청구서 — 선택의 대가를 실제로 청구한다

고르고 끝내면 설문이다. 선택에는 결과가 돌아와야 한다.

| 시점 | 하는 일 |
|---|---|
| 선택 시 | §4 두 안 + §5 변경 압력 예측을 함께 받는다 |
| 구현 | 고른 안으로 민다 (관철하지 않음) |
| **대가가 드러나는 K** (대개 테스트 K, 또는 같은 코드를 다시 건드리는 K) | 예측과 실제를 **대조해 보고** |

보고는 **숫자로** 한다 — 늘어난 스텁 줄 수, 손대야 했던 파일 수, 갈라진 테스트 케이스 수.
"좀 번거로웠다" 는 청구서가 아니다.

- 반대 안이 실제로 더 쌌으면 **그렇게 말한다.** 유지보수 비용 차이는 사실이지 취향이 아니다
- 예측한 압력이 안 왔으면 **안 왔다고 말한다.** 없는 대가를 지어내면 다음 예측이 무의미해진다
- 실행 자리는 `wtflow:commit` 의 완료 보고와 `wtflow:briefing` 이다


## 비고

- 이 규율은 **처리량을 일부러 깎는다.** 그 대가로 얻는 건 작업자가 결과물에 반론할 수 있는
  상태다. 둘 중 뭘 살지는 이슈마다 사용자가 정한다 — 기본값을 조용히 바꾸지 않는다
- 장기적으로는 팀 밖 외부 리뷰 통로(잘 관리되는 오픈소스에 작은 PR 등)가 어떤 프로토콜보다
  크다. 이 문서는 그게 없는 동안의 대체물이다
