# 사전문답 규율

작업을 대신 해 주는 것과 **작업자가 그 코드를 계속 쥘 수 있게 하는 것**은 다른 목표다.
이 문서는 후자를 위해 K 착수 전후에 끼워 넣는 문답 장치를 담는다.
**`plan`·`commit` 이 시작 전에 읽고, `auto` 는 아래 `## 끄는 자리` 규칙에 따라 대부분 끈다.**

브랜치 이름·K 모델·note 계층은 `worktree-discipline.md`, 커밋 메시지 형식은
`commit-convention.md` 를 본다.

**Why:** 완성된 diff 를 읽는 것은 재인(recognition)이라 거의 남지 않는다. 이해는 인출(recall)
에서 붙으므로 브리핑 품질을 올리는 방향으로는 이 문제가 풀리지 않는다. 한편 커밋을 쪼개 보면
도메인 판단이 든 부분은 대개 몇 줄이고 나머지는 기계적이라, **작은 쪽만 사람이 쥐면 처리량
손실이 적다.** 이 규율은 그 비대칭을 노린다.

## 켜는 자리 / 끄는 자리

| | 사전문답 |
|---|---|
| 배울 게 있는 이슈 (도메인 판단·낯선 API·설계 선택) | ✅ 켠다 |
| 급한 작업 / 사용자가 "빨리" 를 명시 | ❌ 끈다 |
| `/wtflow:auto` 를 사용자가 직접 호출 | ❌ 사전 멈춤은 끈다 (§4 예측 문제는 사후로 미룸) |
| 삭제·import 정리·포맷·보일러플레이트 | ❌ 배울 게 없다 — 그냥 진행 |

⚠️ **K 당 5~15분이 늘어난다.** 전부에 켜면 규율이 아니라 마찰이 된다.
plan 이 K 를 낼 때 **어느 K 가 대상인지 먼저 표시**하고, 나머지는 평소대로 민다.

## 1. 예측 후 공개 — 도메인 판단 K 는 구현 전에 멈춘다

plan 이 위치를 특정한 뒤(`file:line`), 도메인 판단이 들어가는 K 는 **구현을 시작하지 않고**
먼저 묻는다.

```
K2 대상은 auth/token.ts:88 입니다. 보시고 —
무엇이 문제고, 무엇으로 바꾸시겠습니까?
```

사용자의 답을 받은 **뒤에** 내 답을 내고 나란히 비교한다. 순서를 뒤집으면
(내 답을 먼저 보이면) 그때부터는 재인이라 장치가 죽는다.

- 위치·근거는 충분히 준다. 아끼는 건 **결론뿐**이다
- 사용자 답이 내 것과 다르면 어느 쪽이 왜 나은지 근거로 다툰다. 사실 문제면 사실로 결론낸다

## 2. 동작 변경 커밋은 사용자가 작성

위험을 지는 코드는 대개 몇 줄이다. 그 몇 줄은 사용자가 쓰고, 나머지는 내가 그대로 민다.

| 누가 쓰나 | 무엇 |
|---|---|
| 사용자 | 동작이 바뀌는 핵심 몇 줄 (§1 로 답이 이미 나온 부분) |
| 나 | 삭제·import 정리·테스트·보일러플레이트·기계적 반복 |

K 를 쪼갤 때부터 이 경계를 만든다 — **동작 변경을 한 커밋에 격리**하면 그 커밋 하나가
곧 사용자 작성분이 된다.

## 3. 사용자가 쓴 코드에는 리뷰어로만 붙는다

고쳐 주지 않고 **지적만** 한다. 네이밍·분할·파라미터 설계에 실제로 반론을 단다.
말없이 다듬어 커밋하면 리뷰가 아니라 대필이 된다.

내가 쓴 코드에는 구조적으로 반박이 불가능하므로, 리뷰가 성립하려면
**사용자가 먼저 쓰고 내가 지적하는 순서**여야 한다.

## 4. 관용구는 메모가 아니라 예측 문제로

비자명한 API 를 썼으면 **설명해 주는 대신 반증 가능한 질문**을 낸다.

```
`ObjectProvider<Foo>` 를 썼습니다.
빈이 0개면 어떻게 됩니까? 2개면? `@Autowired(required=false)` 와 뭐가 다릅니까?
```

답을 받은 뒤 **직접 돌려 확인**하게 한다(5줄 스크래치면 충분). 읽고 끝나는 메모는 남지 않는다.

- 질문은 **틀릴 수 있는 형태**여야 한다. "~를 이해하셨나요" 는 장치가 아니다
- 도는 코드를 먼저 주면 틀릴 기회가 없어져 루프가 안 돈다. 표면이 닫힌 도구(마이그레이션 툴 등)
  에 이해가 잘 붙는 이유가 그것이다 — 예측 문제는 **열린 표면을 닫힌 표면으로 바꾸는 장치**다
- 사전 멈춤을 끈 자리(급한 작업·`auto`)에서도 **예측 문제는 낸다.** 다만 흐름을 끊지 말고
  커밋·브리핑 뒤에 모아서 낸다

## 5. 취향 판단은 두 안을 나란히

주석 스타일·함수 분할·파라미터 설계·모듈화처럼 **취향에 속하는 판단**에서는 한 가지 안을
완성해 주지 않는다. 두 버전을 나란히 내고 고르게 한 뒤 **한 줄로 이유**를 받는다.

- 고르는 데 30초를 넘기지 않을 만큼 **선택지를 좁게** 낸다. `AskUserQuestion` 보기에 각 안의
  코드 스케치를 넣으면 나란히 비교된다
- **정답이 명백한 곳에는 쓰지 않는다** — 진짜로 갈리는 판단에만
- 사용자가 고른 쪽이 내 판단과 달라도 **그대로 간다**(취향 문제에서 내 선호를 관철하지 않는다)
- 단, 동작·성능·안전성에 실제 차이가 있으면 그건 취향이 아니다 — 사실로 알리고 그 근거로 정한다

**Why:** 취향은 설명으로 옮겨지지 않고 비교로만 생긴다. 원래는 자기 코드를 오래 유지보수하며
자기 선택의 대가를 치러야 붙는 종류다. 나란히 놓고 고르게 하는 것이 그 압력의 가장 값싼 대체물이다.


## 비고

- 이 규율은 **처리량을 일부러 깎는다.** 그 대가로 얻는 건 작업자가 결과물에 반론할 수 있는
  상태다. 둘 중 뭘 살지는 이슈마다 사용자가 정한다 — 기본값을 조용히 바꾸지 않는다
- 장기적으로는 팀 밖 외부 리뷰 통로(잘 관리되는 오픈소스에 작은 PR 등)가 어떤 프로토콜보다
  크다. 이 문서는 그게 없는 동안의 대체물이다
