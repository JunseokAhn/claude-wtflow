# 사전문답 규율

작업을 대신 해 주는 것과 **작업자가 그 코드를 계속 쥘 수 있게 하는 것**은 다른 목표다.
이 문서는 후자를 위해 Step 착수 전후에 끼워 넣는 문답 트리거를 담는다. 묻는 이유는 셋으로
갈린다 — **요건 정의·접근방식 선택·변경내용 이해·코드 이해**(`## 네 목적`).
**모든 스킬이 이 문서를 읽는다** — 여기 있는 것은 켜는 자리·질문 형식·질문 전 검사, 즉
**어느 절을 쓰든 걸리는 규칙**이다. 절 자체는 아래 색인의 세 문서에 나뉘어 있다.
`auto` 는 기본으로 순회 중에도 문답을 내고, `--no-ask` 를 받았을 때만 끈다(`## 켜는 자리 / 끄는 자리`).

브랜치 이름·Step 모델·note 종류은 `worktree-discipline.md`, 커밋 메시지 형식은
`commit-convention.md` 를 본다. **섹션을 `§1 예측` 처럼 가리키는 표기는
`writing-style.md` 의 `## 번호 붙은 섹션을 가리킬 때` 를 따른다.**

## 네 목적 — 요건 정의 · 접근방식 선택 · 변경내용 이해 · 코드 이해

절이 열이라 규칙이 절마다 따로 있는 것처럼 보이지만, **묻는 이유는 넷뿐이다.**
앞의 둘은 **사람이 정하는 것**, 뒤의 둘은 그렇게 정하려면 **사람이 알고 있어야 하는 것**이다.

| 목적 | 무엇을 묻나 | 절 | 안 하면 |
|---|---|---|---|
| **요건 정의** | 무엇을 만들지 · 어디까지 되면 끝인지 | §10 수용 기준 | 다 만든 뒤에 다른 걸 만들었음을 안다 |
| **접근방식 선택** | 어떤 방식으로 만들지 — 접근 · 커밋 단위 · 설계 | §8 진행 방향 · §9 커밋 경계 · §4 설계 선택 · §5 변경 시나리오 · §6 유지보수 비용 | 고른 적 없는 구조의 비용을 나중에 치른다 |
| **변경내용 이해** | 이 작업으로 무엇이 달라지는지 | §1 예측 · §11 제품 동작 확인 | 무엇이 달라졌는지 모른 채 다음 작업으로 간다 |
| **코드 이해** | 만들어진 코드가 어떻게 동작하는지 | §7 코드 읽기 | 위임한 코드의 동작을 짐작만 하게 된다 |

- **변경내용 이해와 코드 이해가 헷갈리는 자리** : 변경내용 이해는 **결과를 보고** 답하고,
  코드 이해는 **코드를 열어야** 답한다
- **변경내용 이해만 착수 전후에 걸친다** — §1 예측이 착수 전(무엇을 바꿀 건가), §11 제품 동작 확인이
  커밋 직후(무엇이 바뀌었나). 같은 축의 앞뒤라 한 칸에 둔다
- **정산이 붙는 것은 접근방식 선택뿐이다** — §4 로 고르고 §5 로 수명을 예측한 뒤 §6 이 실제 비용과
  대조. 고르고 끝내면 설문이지 훈련이 아님
- **시점은 목적을 안 정한다** — 계획 단계에 요건 정의(§10)와 접근방식 선택(§9)이 같이 서고,
  커밋 뒤에 코드 이해(§7)와 변경내용 이해(§11)가 같이 선다. 사전·사후로 가르면 이 표가 안 나옴

## 축은 둘이다 — 어느 목적이냐, 그리고 고르는 문항이냐

**`(추천)` 을 붙이는지와 답을 채점하는지는 목적이 아니라 문항 성격이 정한다.** 목적은 어느 자리에서
멈추고 무엇을 묻는지만 정한다. 둘을 한 표로 합치면 예외가 생긴다 — 같은 접근방식 선택 안에서도
§4 설계 선택은 고르는 문항이고 §5 변경 시나리오는 맞히는 문항이다.

| | 고르는 문항 | 맞히는 문항 |
|---|---|---|
| 절 | §4 설계 선택 · §8 진행 방향 · §9 커밋 경계 · §10 수용 기준 · §11 제품 동작 확인 | §1 예측 · §5 변경 시나리오 · §7 코드 읽기 |
| 정답 | 없다 — 사람이 정한다 | 있다 — 코드·실행이 정한다 |
| 첫 보기 `(추천)` | ✅ 붙인다 | ❌ 금지 — 답을 넘겨주는 것이다 |
| 답을 받은 뒤 | 고른 쪽으로 민다 | 채점한다 |

⚠️ **`multiSelect` 면 `(추천)` 을 안 붙인다** — 보기가 여럿 뽑히는 자리라 "첫 보기" 라는 개념
자체가 없다(§10 수용 기준 · §11 제품 동작 확인). 위 표가 정하는 것은 **단일 선택일 때뿐이다.**

- **§4 설계 선택만 두 열에 걸친다** — 고르는 문항인데 채점도 한다. 고른 것을 채점하는 게 아니라
  **그 선택의 수명 예측**(§5 변경 시나리오)을 채점하는 것이고, §6 유지보수 비용이 나중에 실제 비용으로 정산한다
- **정답이 하나여도 되는 것은 §7 코드 읽기뿐이다** — 언어·프레임워크 규칙을 읽는 자리라서다.
  §1 예측·§5 변경 시나리오는 답이 갈려야 한다
- **`--no-ask` 는 목적도 문항 성격도 안 정한다 — 시점이 정한다**
  - 커밋 직후 문항(§7 코드 읽기·§11 제품 동작 확인) : 내지 않음 — 미루면 코드가 이미 머리에서 빠짐
  - 착수 전 문항(§1 예측·§4 설계 선택·§5 변경 시나리오) : 순회 뒤로 미룸
  - 계획 단계 문항(§8 진행 방향·§9 커밋 경계·§10 수용 기준) : 내가 정하고 그 사실을 알림
- **`--no-quiz` 는 §7 코드 읽기 하나만 끈다** — 다른 절은 그대로 낸다(`learning-postcommit.md` 의 `## 한 호출에 담는다`)

## 색인 — 어느 절이 어느 문서에 있나

**자기 이름이 없는 문서는 읽지 않는다.** 그게 이 분할의 목적이다.

| 절 | 문서 | 읽는 스킬 | 무엇을 인출시키나 |
|---|---|---|---|
| §1 예측 · §2 사용자 작성 · §3 리뷰어 역할 | `learning-implementation.md` | `plan` · `commit` · `auto` | **동작 판단** — 무엇이 문제고 무엇으로 바꿀 것인가 |
| §4 설계 선택 · §5 변경 시나리오 · §6 유지보수 비용 | `learning-implementation.md` | `plan` · `commit` · `auto` | **설계 판단** — 어떻게 짤 것인가 |
| §7 코드 읽기 · §11 제품 동작 확인 | `learning-postcommit.md` | `commit` · `auto` | **코드 읽기** — 이 코드가 왜 이렇게 도나 · **동작 확인** — 사용자가 겪는 변화가 의도대로인가 |
| §8 진행 방향 · §9 커밋 경계 | `learning-direction.md` | `issue`(§8) · `plan`(§9) | **선택 단계** — 언제 무엇을 고르나 |
| §10 수용 기준 | `learning-implementation.md` | `plan` · `commit` | **완료 판단** — 반드시 동작해야 하는 것은 무엇인가 |

- **참조는 `§<번호> <이름>` 그대로 적는다 — 파일명을 덧붙이지 않는다.** 어느 문서인지는 이 표가
  답한다. 참조마다 경로를 적으면 절이 옮겨갈 때 고칠 자리가 문서 수만큼 늘어난다
- **§7 코드 읽기만 소재 기준이 다르다.** 나머지는 답이 갈리는 것만 묻지만, 코드 읽기는 정답이 하나여도
  낸다 — 대신 **소재가 있을 때만** 낸다(`learning-postcommit.md` 의 `### 소재를 거르는 기준`)
- 고르는 자리 셋(§8 진행 방향·§9 커밋 경계·§4 설계 선택)이 겹치지 않게 나누는 기준은
  `learning-direction.md` 의 `## 세 단계가 겹치지 않게`

⚠️ **§1 예측·§5 변경 시나리오에서는 정답이 하나인 것이 대상이 아니다.** 계산(`a - b` 가 얼마인가)은 검색하면
나오고, 맞혀도 판단력이 늘지 않는다. 두 절의 소재는 **답이 나뉘고 비용이 따르는 것**뿐이다.

**§7 코드 읽기에는 이 금지가 걸리지 않는다.** 거기서 묻는 것은 언어·프레임워크 규칙이라 정답이
하나이고, 그 하나를 쥐는 것이 목적이다 — 무엇을 소재로 삼을지는 그 절이 따로 거른다.

**Why (동작 축):** 완성된 diff 를 읽는 것은 재인(recognition)이라 거의 남지 않는다. 이해는
인출(recall)에서 붙으므로 브리핑 품질을 올리는 방향으로는 이 문제가 풀리지 않는다. 한편 커밋을
쪼개 보면 도메인 판단이 든 부분은 대개 몇 줄이고 나머지는 기계적이라, **작은 쪽만 사람이 쥐면
처리량 손실이 적다.**

**Why (설계 축):** 설계는 설명으로 옮겨지지 않고 **비용으로만 학습된다.** 원래 그 비용은 자기 코드를
오래 유지보수하며 치른다 — 잘못 자른 경계, 잘못 뽑은 파라미터의 비용이 몇 달 뒤 자기에게 돌아온다.
코드를 위임하면 코드가 늘어나는 속도는 그대로인데 **그 비용을 치를 사람이 사라진다.** 고르게만 하고
끝내는 것은 설문이지 훈련이 아니다. §6 유지보수 비용은 그 비용을 작업 안에서 인위적으로 되살린다.

## 켜는 자리 / 끄는 자리

| | 사전문답 |
|---|---|
| 배울 게 있는 이슈 (도메인 판단·설계 선택) | ✅ 켠다 |
| 구현 Step 안에 **물어야 할 설계 선택**이 있음 (§4 설계 선택 `### 묻는 기준`) | ✅ §4 설계 선택 — **Step 당 최대 하나** |
| 급한 작업 / 사용자가 "빨리" 를 명시 | ❌ 끈다 |
| `/wtflow:auto` 순회 (기본) | ✅ 켠다 — `❓` 가 붙은 Step 앞에서 멈추고 묻는다 |
| `/wtflow:auto --no-ask` | ❌ 전부 끈다 — 커밋 직후 멈춤도 안 선다 (§4 설계 선택·§5 변경 시나리오는 순회 뒤로 미룸) |
| `/wtflow:auto --no-quiz` · `/wtflow:commit --no-quiz` | ❌ §7 코드 읽기만 끈다 — 나머지 문답은 그대로 |
| 삭제·import 정리·포맷·보일러플레이트 | ❌ 배울 게 없다 — 그냥 진행 |
| **동작이 바뀌는 이슈** (§10 수용 기준) | ✅ **계획 단계에 1회** — 작업 항목마다 켜지 않는다 |
| **읽을 만한 코드가 든 커밋** (§7 코드 읽기) | ✅ **커밋 직후에 켠다** — 소재가 없으면 안 켠다 |
| **동작이 바뀌는 커밋** (§11 제품 동작 확인) | ✅ **커밋 직후에 켠다** — 코드 읽기와 같은 호출에 |
| 물어야 할 선택이 그 Step 에 **없음** — 안들의 산출물이 같거나 사실이 답을 정함 (`## 질문을 내기 전 검사` ①②) | ❌ 안 묻는다 — 짜내지 않는다 |
| 물을 것은 있는데 **판단 자료가 덜 붙음** (`## 질문을 내기 전 검사` ③) | ✅ 묻는다 — 인용을 채워서 낸다 |

⚠️ **Step 당 5~15분이 늘어난다.** 마찰은 두 가지로 관리한다 — **개수**(Step 당 §1 예측 하나, §4 설계 선택 하나까지)와
**묻는 기준**(§4 설계 선택 `### 묻는 기준`). 개수만 걸면 질문 수는 줄어도 **"코딩을 직접 하는 기분"** 이 남는다.
질문 하나하나가 구현 세부면 개수를 줄여도 소용없기 때문이다. plan 이 Step 을 낼 때
**어느 Step 이 대상인지 먼저 표시**하고, 대상이 없는 Step 은 없다고 적는다.

## 사전문답은 전부 `AskUserQuestion` 으로 낸다

§1 예측·§4 설계 선택·§5 변경 시나리오·§10 수용 기준 넷 다 예외가 없다. **산문으로 물으면 질문이 아니라 설명이 된다** — 스크롤 위로
흘러가고, 답하지 않아도 대화가 굴러가고, 무엇을 골랐는지 기록에 남지 않는다.
`AskUserQuestion` 은 답을 받기 전에 진행을 막고 선택을 기록으로 남긴다.

| 섹션 | 무엇을 보기로 내나 | 첫 보기 `(추천)` |
|---|---|---|
| §1 예측 | **경쟁 가설** 2~4개 — 그중 하나가 정답 | ❌ **금지** — 답을 넘겨주는 것이다 |
| §4 설계 선택 | 설계안 2~3개 + 코드 스케치 (자리는 `### 어디에 두나`) | ✅ 필수 |
| §5 변경 시나리오 | 먼저 닥칠 시나리오 2~4개 | ❌ 금지 — 채점 대상이다 |
| §7 코드 읽기 | 방금 커밋한 코드의 **동작 보기** 3~4개 — 정답이 하나여도 된다 | ❌ 금지 — 맞히는 자리다 |
| §11 제품 동작 확인 | **바뀐 동작** 2~4개 + 「전부 의도대로다」 (multiSelect) | ❌ 금지 — multiSelect 라 첫 보기 규칙이 없다 |
| §10 수용 기준 | 이슈 전체의 **완료 조건** 5~7개 (multiSelect, 5개까지 선택) | ❌ 금지 — multiSelect 라 첫 보기 규칙이 없다 |

**`(추천)` 을 붙이는 곳과 붙이면 안 되는 곳이 다르다 — 가르는 것은 문항 성격이다**(`## 축은 둘이다`).
§4 설계 선택은 **고르는 문항**이라 판단 기준을 함께 줘야 하지만(`### 형식`), §1 예측·§5 변경 시나리오는
답을 **맞히는 문항**이다. 거기에 추천을 달면 그 순간 채점이 끝나고 트리거가 안 걸린다.
이 저장소의 다른 스킬이 지키는 "첫 보기 `(추천)`" 규칙을 **맞히는 문항이 깨는 이유**가 그것이다.
`multiSelect` 문항(§10 수용 기준·§11 제품 동작 확인)도 안 붙이지만 까닭이 다르다 — `## 축은 둘이다`.

- **한 Step 의 문항은 한 번의 호출에 모은다** — `❓` 문항(§1 예측·§4 설계 선택·§5 변경 시나리오)은
  **최대 3개**, 진행 여부 문항까지 합쳐 **4문항**(도구 상한). 호출을 나누면 Step 하나에 멈춤이
  세 번 생겨 마찰이 배로 든다
  - **예외는 인용 턴 하나다** — 문항 중 하나라도 preview 를 넘는 인용이 있으면 그 Step 의 문항 전부를
    질문 턴으로 미룬다. 인용 턴이 멈춤 하나를 더하지만 호출은 여전히 한 번이다
    (§1 예측 `### 어디에 두나`)
- **§10 수용 기준은 이 셈에 안 든다** — 계획 단계에서 §9 커밋 경계와 같은 호출에 1회 나가고,
  Step 착수 자리에는 오지 않는다
- ⚠️ **"다음 Step 으로 갈까요?" 를 따로 묻지 않는다 — 그 Step 의 `❓` 와 같은 호출에 담는다.**
  둘로 나누면 진행 여부가 산문으로 새 나가고(이 섹션의 의무를 빠져나간다), 사용자가 "가자" 라고
  답한 뒤에야 질문이 나가 멈춤이 두 번이 된다. **가장 흔한 누락이 여기다** — 앞 Step 을 커밋하고
  나면 다음 Step 의 `❓` 를 낼 자리가 없어져 조용히 건너뛰게 된다.
  진행 여부는 첫 문항(보기: 이 Step 진행 / 다른 Step 부터 / 여기서 멈춤)으로 넣고, `❓` 문항을
  같은 호출에 이어 붙인다. 진행을 안 고르면 뒤 문항 답은 버리면 된다
- **자유 입력은 자동 "Other" 로 보장된다.** "직접 입력" 보기를 따로 넣지 않는다. 자기 말로
  답하고 싶으면 Other 로 쓰면 되고, **그게 §1 예측의 원래 형태(인출)에 가장 가깝다**
- **보기가 답을 가리지 않게 만든다.** §1 예측의 오답 보기는 *그럴듯해야* 한다. 한눈에 틀린 게
  보이는 들러리를 세우면 고르는 순간 정답이 드러나 재인조차 성립하지 않는다
- **판단 자료를 인용한다**(`### 질문은 자족적이어야 한다`). `AskUserQuestion` 을 쓴다고 해서
  `file:line` 만 던져도 되는 게 아니다 — **어디에 두는지까지 그 섹션이 정한다**.
  붙였는지는 `## 질문을 내기 전 검사` ③·④ 로 센다 — **보기가 부른 이름과 판정 조건을 인용과 대조**한다
- 답을 받은 **뒤에** 내 답을 낸다(§1 예측) / 그 자리에서 채점한다(§4 설계 선택 `### 답 직후 즉시 채점`)
- **틀렸으면 정답 보기의 라벨을 그대로 다시 적는다.** 답을 보내면 화면에서 질문이 접혀 보기가
  사라진다 — `정답은 1번입니다` 만 쓰면 그 1번이 무엇이었는지 받는 쪽 화면에 없다.
  **고른 보기와 정답 보기를 라벨째 적고 번호로 대신하지 않는다.** 맞았으면 정답 라벨만 한 번
  - ❌ `정답은 1번입니다. await 는 바로 뒤 표현식 하나에만 걸립니다`
  - ✅ `고르신 것 : 「반복마다 기다린다」 / 정답 : 「반복 전에 한 번 기다려 배열을 받는다」 — await 는 …`
- **채점·공개 분량은 `writing-style.md` 의 `## 응답의 셀 수 있는 상한` 이 센다** — 대상은 답을
  받은 뒤 내는 내 답(§1 예측·§4 설계 선택·§5 변경 시나리오·§7 코드 읽기)
  - 인용·판단 자료는 셈에서 제외 — 근거를 줄이라는 뜻이 아님
  - 근거를 다 펼치면 채점이 아니라 해설 → 더 필요하면 사용자가 되물음
- `/wtflow:auto` 는 기본으로 순회 중에도 이 호출을 한다. `--no-ask` 면 하지 않고 순회 뒤로 모아 낸다

**Why:** 산문 질문은 답을 안 받아도 대화가 굴러가서 트리거가 조용히 안 걸린다. 보기를 주면 인출이
재인으로 한 단계 내려가는 손실이 있지만, **답하지 않고 지나가는 것보다는 낫다.** 그 손실은
Other 자유 입력과 "그럴듯한 오답" 두 가지로 줄인다.

### 「없음」 이 성립하는 질문에는 「없음」 보기를 넣는다

**보기가 전부 "무언가 일어난다" 형태면 답이 하나 이상 있다고 전제한 것이다.** 사용자가 "없다" 로
판단해도 낼 수단이 없어 아무거나 고르게 된다 — 강제 오답이고, 채점이 성립하지 않는다.

| 절 | 「없음」 보기 문구 |
|---|---|
| §1 예측 | 아무것도 안 깨진다 · 지금도 정상이다 |
| §5 변경 시나리오 | 무엇이 바뀌어도 이 선택은 안 고친다 |
| §11 제품 동작 확인 | 결과가 달라지지만 전부 의도대로다 |

- **넣는 기준은 「없음」 이 답인지가 아니라 「없음」 이 성립하는 질문인지다.** 내가 보기에 답이
  분명해도 넣는다 — 안 넣으면 그 질문은 답을 이미 좁혀 놓은 것이다
- **아무것도 안 고르고 Submit 하는 것으로 대신하지 않는다.** multiSelect 에서 빈 답은
  **"없다고 답한 것" 과 "넘긴 것" 이 구분되지 않는다** — 채점자가 어느 쪽인지 모른다
- **「없음」 을 고르면 그것도 채점한다.** 내 판정과 대조하고 근거를 낸다 — 고르면 넘어가는
  보기가 아니다
- **다른 보기와 같이 고르면 모순이다.** 「없음」 + 바뀐 동작 2개를 함께 고르면 그 자리에서
  알리고 다시 받는다
- §10 수용 기준에는 안 넣는다 — 조건이 없으면 `## 질문을 내기 전 검사` ① 이 먼저 걸러
  질문 자체가 안 나간다

## 질문을 내기 전 검사 — 고를 것이 있나, 답할 수 있나

`## 켜는 자리 / 끄는 자리` 는 **어느 Step 에** 묻는지를 정하고, §4 설계 선택 `### 묻는 기준` 은
**어느 결정을** 묻는지를 정한다. 둘 다 통과한 질문이라도 **보기가 실제로 다른지**, 그리고
**받는 쪽이 그 보기를 판별할 수단을 손에 쥐었는지**는 아무도 재지 않았다. 그래서 산출물이 같은
안 둘을 세운 질문과, 인용에 없는 코드를 이름으로 부르는 질문이 나갔다.

§1 예측·§4 설계 선택·§5 변경 시나리오·§7 코드 읽기·§8 진행 방향·§9 커밋 경계·§10 수용 기준 —
`AskUserQuestion` 을 부르기 직전에 아래 넷을 검사한다.

| 검사 | 어떻게 아나 | 걸리면 |
|---|---|---|
| ① **안마다 산출물이 다른가** — 코드·설정·작업 항목이 달라지는 지점이 있나 | 안별 산출물을 나란히 놓고 대조 → 다른 줄이 없음 | 묻지 않는다 — 고를 것이 없다 |
| ② **사실이 이미 답을 정하나** — 저장소 관용구·동작·계약이 한쪽을 이미 고르고 있나 | 저장소에 같은 문제를 푼 자리가 있고 그 방식이 하나 | 묻지 않는다 — 사실로 알리고 그 근거로 정한다 |
| ③ **인용을 검색으로 채웠나** — §1 예측 `### 인용은 만들 때 도구로 채운다` 의 3·4단계를 거쳤나 | 보기·질문 본문·인용 안 호출의 이름마다 검색을 돌렸는지 본다 → 안 돌린 이름이 있음 | **질문을 지우지 않고 인용을 채운다** — 못 채우면 그 보기를 뺀다(§7 은 예외, 아래) |
| ④ **판정 조건을 역산했나** — 같은 절차의 2단계(판정 조건 문장)를 거쳤나 | 보기마다 "무엇이 참이면 이 답인가" 를 한 문장으로 적고, 그 참·거짓을 정하는 코드가 인용에 있는지 본다 → 없고 "추적 못 함" 도 없음 | **질문을 지우지 않고 인용을 채운다** — 끝까지 못 찾으면 어디까지 찾았는지와 함께 추적 못 했다고 적는다 |

**①② 와 ③④ 는 걸렸을 때 하는 일이 반대다.** ①② 는 *물을 것이 없다* 는 판정이라 질문을 지우고,
**건너뛴 사실과 걸린 검사를 한 줄로 적는다.** ③④ 는 *물을 것은 있는데 답할 수단이 빠졌다* 는
판정이라 인용을 채워 그대로 낸다 — 여기서 질문을 지우면 걸러야 할 것이 안 걸러진다.

- ① 은 §8 진행 방향 `### 건너뛰는 조건` 의 "안이 2개를 못 채우면 묻지 않는다" 와 같은 뜻이다 —
  다만 **개수가 아니라 산출물로** 센다. 이름만 다른 안 둘은 1개다
- ② 는 동작·성능·안전성·공유 계약의 실제 차이에 **저장소 관용구까지** 더한 것이다. 같은 문제를
  이미 한 방식으로 풀어둔 자리가 있으면 그 방식이 답이고, 다른 안은 그 관용구를 깨는 안이다
- **본문에 "어느 안이든 같다" 류 문장이 써지면 그 자리가 ① 위반이다.** 질문을 쓰다가 그 문장이
  나오면 질문을 지운다
- ③ 이 기계적인 것은 **대조가 아니라 검색**이다. 무엇을 붙일지 고르는 판단은 §1 예측의
  절차가 앞에서 없앤다 — 이 검사는 그 절차를 안 거친 이름을 찾을 뿐이다
- ③ 에서 뽑는 대상은 셋이다 — **보기의 라벨·설명 줄**, **질문 본문이 사실로 주장한 문장**,
  **인용한 코드가 부르는 이름 중 답이 그 반환값·동작에 걸리는 것**. 세 번째가 가장 안 걸린다 —
  코드를 붙였다는 사실이 대조를 대신해 버린다. 다만 인용이 부르는 것 전부는 아니다:
  `thumbnailOf(n) && <Thumb/>` 은 썸네일이 뜨는지가 답이라 걸리고 `useCallback` 은 안 걸린다
- ③ 은 **`file:line` 주석을 인용으로 치지 않는다.** 무엇을 붙이고 어디에 두는지는
  §1 예측 `### 질문은 자족적이어야 한다` 와 `### 어디에 두나` 가 정한다
- ③ 은 **설명 주석도 증거로 치지 않는다.** `// typeCount 는 visible 만 센다` 는 붙이는 쪽의
  진술이지 받는 쪽이 확인할 코드가 아니다 — 사실을 주장하려면 **그 사실을 만드는 줄**을 붙인다.
  포인터 주석보다 이쪽이 안 걸린다. 코드처럼 생겨서 붙인 쪽도 대조를 건너뛴다
- **④ 는 ③ 과 따로 둔다 — ③ 을 기계적 검색으로 남기기 위해서다.** ③ 은 나온 이름을 셀 뿐이라
  **보기·본문·인용 어디에도 이름이 안 나온 조건은 대상이 안 된다.** 설정 한 줄·검증 함수·값의 출처가
  대개 그렇다. 조건 문장을 쓰는 데는 판단이 들어서, ③ 에 섞으면 ③ 의 "검색만 한다" 가 깨진다
- ④ 의 조건 문장은 **질문에 싣지 않아도 된다** — 무엇을 찾을지 정하는 용도다. 싣는 것은 그 문장이
  찾게 한 코드와, 못 찾았으면 "추적 못 함" 이다
- ④ 는 **보기의 참·거짓이 코드에 달린 질문**에만 건다(§1 예측·§5 변경 시나리오·§7 코드 읽기가 대부분).
  작업 항목안을 고르는 §8·§9 처럼 판정이 코드가 아니면 해당 없음

### 반례 ① · ② — 검사 없이 나간 질문

CI 배포 잡의 이미지 태그를 정하는 작업에서 나간 질문이다. 본문이 스스로 이렇게 적었다:

> 폴백 식은 어느 안이든 같습니다:
> `IMAGE_TAG="${ORIGIN_TAG:+${ORIGIN_TAG}-}${ORIGIN_COMMIT_SHORT}"`
> …
> `.gitlab-ci.yml` 은 이미 `.get_aws_role: &get_aws_role` 처럼 앵커로 공통 prelude 를 나눠 쓰는
> 관용구가 자리잡은 파일입니다.

| 검사 | 이 질문에서 |
|---|---|
| ① 안마다 산출물이 다른가 | 식이 어느 안이든 같다고 본문이 적음 → **위반** |
| ② 사실이 이미 답을 정하나 | 앵커 관용구가 자리잡았다고 본문이 적음 → 공통 prelude 를 어디 둘지는 이미 정해진 것 → **위반** |

둘 다 본문 안에 증거가 있었다. 검사가 없어서 질문이 그대로 나갔다.

**Why:** 묻는 기준을 통과한 Step 에서 "그러면 무엇을 묻지" 로 넘어가면 안을 **만들게** 된다.
만든 안도 형식(판단 기준 한 줄·preview·`(추천)`)은 전부 갖추고 나가므로 형식 검사로는 안 걸린다.
걸리는 건 산출물 대조뿐이다.

### 반례 ③ — 부른 이름이 인용에 없는 질문

**앞의 넷**은 enum 에 상수 하나를 더하면 무엇이 깨지는지 묻는 §1 예측이다. 질문 앞 본문에
코드를 네 덩이 붙였는데도 사용자가 **"그 코드가 안 보이는데 어떻게 판단하나"** 로 되물었다.
**뒤의 둘**은 다른 질문 — 커밋 하나의 소비처 넷을 낸 영향 범위 질문이다(지금은 폐지). 거기서는 문제의 이름이
**보기에 아예 없어** 보기만 훑는 대조로는 안 걸렸다.

| 부른 자리 | 부른 이름 | 인용에 몸통이 있었나 |
|---|---|---|
| §1 보기 「아무것도 안 깨진다」 | — | 해당 없음 |
| §1 보기 「`findSeedOrNull` 이 컴파일되지 않는다」 | `findSeedOrNull` | ❌ switch 식만 잘라 붙였고 **메서드 시그니처가 없어** 이름과 이어지지 않았다 |
| §1 보기 「`KgNodeId.parse` 가 깨진다」 | `KgNodeId.parse` | ❌ 그 메서드가 쓰는 상수 하나만 있었다 |
| §1 보기 「런타임에 터진다」 | — | 해당 없음 |
| 영향 범위(폐지) **질문 본문**이 사실로 주장 | `thumbnailOf` | ❌ 인용에 호출만 있고 몸통이 없다. "데이터 노드만 썸네일이 있다" 는 커밋 diff 밖 사실이라 `git show` 로도 안 나온다 |
| 영향 범위(폐지) **인용 안 주석**이 사실로 주장 | `typeCount` | ❌ `// visible 안의 노드를 센 Map 이다 (:200-205)` 뿐이었다 — 주석은 붙이는 쪽의 진술이지 확인할 코드가 아니다 |

붙인 코드의 양은 적지 않았다. 걸러내지 못한 이유는 **"코드를 붙였나" 를 셌기 때문**이다.
세야 하는 것은 **"부른 이름이 그 코드 안에 있나" 다.**

**Why:** 자족성 규칙은 "답에 필요한 코드를 붙인다" 라고 쓰여 있다. 무엇이 필요한지는 쓰는 쪽이
판단하는데, **쓰는 쪽은 이미 코드를 다 읽은 상태**라 무엇이 빠졌는지 보이지 않는다. 이름을
인용과 대조하는 것은 그 판단을 거치지 않고 기계적으로 센다 — ①② 가 산출물 대조로만 걸리는 것과 같다.
뒤의 두 행이 **대조할 자리를 보기로 한정하면 안 되는 이유**다.

### 반례 ④ — 판정 조건이 어디에도 이름으로 안 나온 질문

반환 페이로드에 필드 둘을 더한 커밋의 영향 범위 질문이다(지금은 폐지). 소비처는 둘 — 다른 서비스에서 그 페이로드를
타입 있는 레코드로 역직렬화하는 구독자, 프런트에서 페이로드를 그림 데이터로 바꾸는 파서였다.
질문에는 레코드 선언과 두 진입 함수를 붙였는데 사용자가 **"밑도 끝도 없다"** 로 되물었다.

| 보기 | 판정 조건 (무엇이 참이면 깨지나) | 조건을 정하는 코드 | 첫 질문에 있었나 |
|---|---|---|---|
| 구독자 | 역직렬화기가 레코드에 없는 필드를 받으면 에러를 낸다 | 전역 매퍼의 `FAIL_ON_UNKNOWN_PROPERTIES` 설정 한 줄 | ❌ |
| 파서 | 새 bbox 가 검증 함수를 통과하지 못한다 | 검증 함수 몸통 | ❌ |
| 파서 | 넘기는 캔버스 크기가 페이로드와 다른 좌표계다 | 캔버스 크기를 채우는 자리(값의 출처) | ❌ — 다시 낸 질문에서도 끝까지 못 찾아 "추적 못 함" 으로 적었다 |

셋 다 **보기·질문 본문·인용 어디에도 이름이 없어** ③ 을 통과했다. 조건 문장부터 쓰고 찾게 하자
세 코드가 나왔고, 다시 낸 질문에는 바로 답이 나왔다.

**Why:** ③ 은 "부른 이름이 인용에 있나" 를 센다. 판정을 가르는 코드는 **아무도 부르지 않은 이름**이라
그 셈에 안 걸린다. 무엇을 찾을지를 이름이 아니라 **조건 문장**에서 뽑아야 한다.

## 비고

- 이 규율은 **처리량을 일부러 깎는다.** 그 대신 얻는 건 작업자가 결과물에 반론할 수 있는
  상태다. 둘 중 뭘 살지는 이슈마다 사용자가 정한다 — 기본값을 조용히 바꾸지 않는다
- 장기적으로는 팀 밖 외부 리뷰 통로(잘 관리되는 오픈소스에 작은 PR 등)가 어떤 프로토콜보다
  크다. 이 문서는 그게 없는 동안의 대체물이다
