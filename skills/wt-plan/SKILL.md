# /wt-plan — 이슈 기반 워크트리 시작

## 호출

`/wt-plan <이슈번호> [-b <base>] [-p <prefix>] [-r <repo>]`

- `<이슈번호>` (필수): glab으로 본문/라벨 조회
- `-b <base>`: 분기 베이스 브랜치. 미지정 시 `origin/develop` (없으면 `origin/main`)
- `-p <prefix>`: 브랜치 prefix. 미지정 시 이슈 라벨에서 추론
  - `종류:버그` → `fix`
  - `종류:기능` → `feat`
  - `종류:리팩터링` → `refactor`
  - 그 외 / 추론 실패 → `chore` (사용자 확인)
- `-r <repo>`: glab repo (예: `<org>/<repo>`). 미지정 시 현재 git remote에서 자동 추론

## 계약 (보장되어야 하는 것)

1. **이슈 메타 로드** — `glab issue view <N> -R <repo>`로 제목·라벨·본문 가져옴. 실패 시 중단·보고

2. **현재 워크트리 감지** — `git rev-parse --show-toplevel` + `git worktree list` 로 현재 위치가 main 워킹트리가 아닌 워크트리인지 판정
   - **워크트리 안** (예: claude --worktree 로 진입한 경우, 또는 wt-issue 후 진입) → 3·4·5 skip, 6단계로
   - **워크트리 밖** → 3·4·5 실행

3. **(워크트리 밖일 때) 이름 안 제시 + 사용자 확인 한 번**:
   - 워크트리 브랜치: `<prefix>/<N>-<slug>` (`#` 없음 — `claude --worktree` 가 `#` 거부, wt-commit accumulator 도 `#` 없는 쪽). 기존 브랜치가 origin/local 에 있으면 재사용. 없으면 wt-issue 와 동일 컨벤션으로 신규
   - 워크트리 경로: `<repo-root>/.claude/worktrees/<prefix>+<N>-<slug>`
   - slug는 제목의 한국어를 의미 기반 영어 kebab-case로 (최대 5단어)

4. **(워크트리 밖일 때) 워크트리 생성** — `git fetch origin && git worktree add <경로> <브랜치>` (브랜치 기존 사용 시 -b 없음 / 신규 시 `-b <브랜치명> origin/develop`)

5. **(워크트리 밖일 때) 세션 working directory 이동** — `cd <워크트리경로>` (이 세션에서 이후 명령이 워크트리에서 실행됨)

6. **이슈 본문 출력** — 후속 작업의 컨텍스트로 표시. 코드 분석 시작 안내만 하고 수정은 사용자 승인 후
7. **plan 출력** — 이슈 본문/라벨 + **코드 분석 결과**로 작업 단계 추정 (아래 `## plan 출력 형식` 참고). 자동 실행 안 함, 가이드 용도

## 결정·중단 트리거

- 이슈 미존재 / glab 인증 실패 → 보고 후 중단
- 동일 이름 워크트리/브랜치 이미 존재 → 사용자에게 재사용 vs 신규 선택
- base 브랜치 fetch 실패 → 중단·보고
- prefix 추론 실패 → 사용자에게 묻고 대기
- 현재 디렉토리가 git 워킹트리 루트가 아님 → 보고 후 중단
- 워크트리 안인데 현재 브랜치명이 이슈 번호와 불일치 → 사용자에게 경고 + 진행 여부 확인

## 짧은 변형

- "베이스는 main 으로" → `-b origin/main`
- "feat 로" → `-p feat`
- "plan 빼고" → 계약 6번 생략 (이슈 본문만 출력)
- "plan만 간단히" → 코드 분석 없이 이슈 본문만으로 plan

## plan 출력 형식

### 절차

1. **키워드 추출**: 이슈 제목·본문에서 도메인 명사·함수명·파일명·에러 메시지·클래스명 등 식별 가능한 토큰 추출
2. **관련 파일 탐색**:
   - 파일명 유사 / 경로 패턴 → Glob (예: `**/*Annotation*.kt`)
   - 함수·식별자·에러 메시지 → Grep
   - 결과는 step의 "관련 파일/위치" 열에 file:line 형식으로 포함
3. **step = 이슈 작업 항목**: 이슈 본문의 `작업 항목` 을 **그대로 Step 으로 매핑**한다 (작업 항목 N = Step N = K N). 코드 분석(1·2)은 새 step 을 만드는 게 아니라 **각 작업 항목의 "관련 파일/위치"를 채우는 용도**. 작업 항목이 비어 있거나, 한 항목이 단독 commit 으로 감당 안 될 만큼 크면 그때만 보조 분해(하위 a/b)하되 **K 는 작업 항목 번호에 고정**한다 (한 작업 항목 = 한 K = 한 mirror 분기, 커밋은 그 안에 누적)
4. **표 출력** (Step 열 = 이슈 작업 항목 번호 = K):

| Step | 설명 | 관련 파일/위치 | 권장 호출 |
|------|------|----------------|-----------|
| 1 | <한 줄 요약> | `path/to/file.kt:42`, `path/to/other.kt` | `/wt-commit "<커밋 메시지>" -K 1` |
| 2 | ... | ... | `/wt-commit "..." -K 2` |
| ... | ... | ... | ... |

### step 분할 감각 (작업 항목이 비었을 때 폴백)

이슈에 `작업 항목` 이 있으면 그대로 Step·K 로 쓴다 (위 3번). 아래는 작업 항목이 **없거나** 큰 틀 보정이 필요할 때의 분할 감각일 뿐, 작업 항목을 무시하고 새로 쪼개라는 뜻이 아니다.

- **bug 류**: 재현 → 원인 격리 → 수정 → 회귀 테스트. 보통 2-4 step
- **feature 류**: 데이터 모델/계약 → 핵심 로직 → 통합/UI → 테스트. 보통 3-6 step
- **refactor 류**: AS-IS 식별 → 변환 전략 → 단계별 변환 (의존성 역순). 작업 크기에 따라 가변
- **infra/chore 류**: 단일 commit으로 충분한 경우 많음. 굳이 잘게 쪼개지 말기
- **공통 원칙**: 한 step = 한 의미 단위 (단독 commit·revert 가능한 최소 단위). 너무 잘면 noise, 너무 크면 회복 어려움

### K 매핑 원칙

- **step 번호 = K 번호 = 이슈 작업 항목 번호** (작업 항목 N 완료 시 `-K N`, mirror 분기 `-00N`)
- 4단계 이상 또는 1주 이상 예상 → 통합 브랜치 + accumulator 패턴 권장
- 1-2단계 → 굳이 분해 없이 작업 후 `/wt-commit` 1회로 충분
- 자동 실행 안 함 — 각 step 끝에 사용자가 직접 호출
- plan 자체가 자주 틀림 — 진행 중 자연어로 재조정 가능. 그 시점부터 K 번호만 일관되게 유지하면 됨

복잡한 plan/일반 작업 분해가 필요하면 워크트리 무관한 일반 작업 분해 도구를 별도로 쓴다

## 이후 흐름

- 워크트리 안 커밋은 `/wt-commit <설명> [-K <N>]` — **작업 항목(K)=분기, 그 안 태스크마다 커밋해 누적**. 한 작업 항목의 여러 태스크를 커밋 없이 한 덩어리로 진행 금지(사용자 batch 명시 시 예외)
- **작업 항목(K) 완료 시 이슈 체크박스 자동 체크** — wt-commit/wt-auto 가 이슈 본문 N번째 작업 항목을 켠다(상세는 wt-commit). plan 의 K 매핑이 곧 체크박스 순서이므로 K 를 작업 항목 번호에 정확히 고정할 것
- step 번호 = K 번호 (plan 출력 표의 매핑 그대로)
- mirror 브랜치 `<prefix>/<N>-<slug>-NNN`이 K+1씩 증가하며 origin push
- 코드 수정·테스트·MR 생성 시점은 사용자가 결정
- plan 변경 시 다음 `/wt-commit` 호출에 새 K 번호 직접 지정

## 비고

- 워크트리 브랜치는 origin에 push 안 함 (로컬 전용 작업 공간)
- mirror 분기 브랜치만 origin에 노출
- 세션의 표시상 Primary working directory는 시작 시점 값으로 고정. 실제 명령은 cd 이후 워크트리에서 실행됨
