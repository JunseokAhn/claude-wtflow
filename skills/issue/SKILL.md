# /wtflow:issue — GitLab 이슈 생성·본문 재작성

**시작 전에 `${CLAUDE_PLUGIN_ROOT}/references/worktree-discipline.md`(브랜치 이름 규칙·K 모델·note 계층)를 읽는다.**

## 트리거

**생성**

- 자연어: "이슈 만들어줘: <설명>", "이슈 등록", "GitLab에 올려줘", "이슈로 등록" 등
- 슬래시: `/wtflow:issue <설명> [-R <group>/<repo>]`

**재작성** (아래 `## 재작성 모드`)

- 자연어: "이슈 본문 다시 써줘", "이슈 #14 갱신", "이슈 내용 고쳐줘", "이슈에 <내용> 반영해줘" 등
- 슬래시: `/wtflow:issue --rewrite <N> [-t "<새 제목>"] [-R <group>/<repo>]`

⚠️ **이슈 본문을 바꾸는 경로는 재작성 모드 하나다.** `glab issue update -d` 를 직접 부르지 않는다 —
훅이 막는다(`hooks/guard-body-edit.sh`). 유일한 예외는 wtflow:commit 의 체크박스 동기화다.

## 마일스톤은 이 스킬의 관심사가 아니다

**마일스톤 이슈든 단독 이슈든 이 스킬이 하는 일은 같다** — 제목·라벨·본문을 만들어 이슈를 생성한다.

- 마일스톤을 **조회하지 않는다** — `glab` 마일스톤 API 호출, `_milestone/` 디렉토리 탐색 금지
- **마일스톤 배정도 하지 않는다.** 그건 `/wtflow:milestone` 계약 8b 몫이고, 그 배정이 나중에
  `/wtflow:plan` 이 마일스톤 계약을 찾는 유일한 근거가 된다
- 이슈 본문에는 어차피 마일스톤 문서를 가리킬 수 없다(계약 4 — 팀원에겐 없는 로컬 파일이다).
  그래서 이 스킬이 마일스톤 여부를 알아야 할 이유가 없다

**Why:** 스킬 호출은 컨텍스트를 공유해서, 산문으로 넘긴 맥락은 단독 이슈에까지 새어든다.
아예 판정하지 않으면 오염될 것도 없다.

## 계약

1. **prefix 추정** (제목 첫머리):
   - 버그 수정 의도 → `fix:`
   - 새 기능 → `feat:`
   - 리팩터링 → `refactor:`
   - 문서 → `docs:`
   - 테스트 → `test:`
   - 그 외·모호 → `chore:` (사용자 확인)

2. **라벨 3종 결정** — 아래는 실제 라벨 값(본인 표준). **없는 라벨을 만들지 말 것** — 의심되면 `glab label list -R <repo>`로 검증:
   - **종류** (필수, `종류:*`): prefix 매핑 자동 — 값은 **기능 / 리팩터링 / 버그 / 인프라** 넷뿐
     - `fix:` → `종류:버그`
     - `feat:` → `종류:기능`
     - `refactor:` → `종류:리팩터링`
     - `chore:` → `종류:인프라`
     - `docs:` / `test:` / `perf:` / `style:` → 전용 종류 없음 → `종류:인프라`(일반 버킷)로 두되 확인 단계에서 조정
   - **난이도** (`난이도:낮음` · `난이도:보통` · `난이도:높음`): 추정 어려우면 **보통** default (※ 쉬움/어려움 아님 — 낮음/높음)
   - **우선순위** (`우선순위:낮음` · `우선순위:보통` · `우선순위:높음` · `우선순위:긴급`): 추정 어려우면 **보통** default

3. **제목 생성**: `<prefix> <한국어 한 줄 요약>` — scope 를 붙여 `<prefix>(<scope>): …` 로 써도 된다
   - **명사구로 끝낸다** (`…추가` · `…제거` · `…전환` · `…정리` · `…방지` · `…누락`). **서술형 종결 금지** — `~한다` · `~하도록 함` · `~옮김` · `~막음`
   - **두 산출물이면 접속사 말고 `+`** — ✅ `feat(search): 이미지 검색 API 추가 + 결과 화면 연동` / ❌ `feat(search): 검색 API 를 만들고 화면에 연동한다`
   - **보충은 괄호 하나까지** — `fix(upload): 동시 요청 시 파일명 중복 방지 (유니크 인덱스)`
   - **식별자·영어는 원문 유지** — 코드에 있는 이름(상수·함수·API·설정 키)은 그대로 쓴다. 억지로 한글화하면 검색이 안 된다
   - 예: `fix: 사용자 로그인 시 토큰 만료 에러` · `refactor(auth): 세션 저장소를 서버 측 만료 방식으로 이관`
   - **커밋 제목과 같은 규칙이다** — `references/commit-convention.md` 의 `## Subject` 를 이슈 제목에도 그대로 적용한다(한쪽만 고치면 갈린다)

4. **본문 작성** — 저장소 이슈 템플릿 우선 사용 (아래 `## 본문 템플릿` 참고). 템플릿 없으면 한 줄 요약
   - **이슈는 "무엇/왜"의 짧은 메모다.** 근본원인 분석·코드경로·클래스명 나열·해결책 설계·세부 작업분해는 이슈에 쓰지 않는다 — 그건 이후 `/wtflow:plan` plan 단계 몫이다. 지금 이슈에 결론을 박으면 plan 과 중복되거나 어긋난다
   - **서술 절은 목록이 기본** — `배경`·`현상`·`목적`·`요약`·`상세 설명`처럼 사실을 늘어놓는 절은 문단 대신 목록으로 쓴다. **한 줄에 한 사실.** 두 문장으로 끝나는 이슈는 문단도 된다. 다만 **세 문장을 넘기는 순간 목록으로 바꾼다** — 문단이 길어지면 훑어서 요점을 집을 수 없다
     - `작업 항목` 체크리스트는 이 규칙과 무관하다 — 그 형태는 진행 상태를 읽는 쪽이 의존하므로 손대지 않는다 (`- [ ] <번호>. `)
     - 같은 취지의 규칙이 이미 `/wtflow:milestone` 에 있다. 이 줄은 그걸 **이슈 본문까지 넓힌 것**이고, 어휘를 새로 만들지 않는다
   - **이미 상세히 계획해둔 게 있으면 이슈에 밀어넣지 말고 note 로 흘려보낸다** (계약 8). 페이로드 계약·타입·에러코드·호출 순서 같은 것이 여기 해당한다. 여러 이슈·레포가 공유해야 하는 계약이라면 `/wtflow:milestone` 의 마일스톤 note 가 목적지다
   - ⚠️ **이슈는 자족적이어야 한다 — wtflow 를 전혀 모르는 글로 쓴다.** 팀원에겐 `~/.claude/notes/` 가 없다. **어느 섹션에도**(`참고 자료` 포함 — 여기가 제일 잘 샌다) 쓰지 않는다: note 의 **절 이름 참조**(~~"계약 상세는 마일스톤 문서 … 절 참조"~~), **로컬 경로·파일명**(`.claude/…`, "마일스톤 문서"), **내부 용어**(K 번호·mirror 분기·accumulator·워크트리).
     맥락이 더 필요하면 가리키지 말고 **그 내용을 직접 풀어 쓴다.** `참고 자료` 에는 팀원이 실제로 열 수 있는 것만(GitLab 링크·외부 URL·Notion)

5. **사용자 확인 한 번 — 산문 말고 `AskUserQuestion`**: 본문 미리보기를 보인 뒤, 조정 가능한 축(prefix/종류·난이도·우선순위)을 **`AskUserQuestion` 으로 묻는다**(산문으로 "이대로 생성할까?" 나열 금지 — 이게 가장 흔한 누락). 각 보기 첫째에 추천안을 `(추천)` 으로 표기. 자유 입력 경로는 클라이언트가 자동으로 붙이는 "Other" 로 보장되므로 **"직접 입력" 보기를 따로 넣지 않는다**(여기 질문은 prefix·라벨처럼 보기가 유한해서 Other 한 줄이면 충분하다. 반대로 사용자가 **값을 지어내야 하는** 질문 — 페이로드 필드·에러코드 같은 것 — 에는 `직접 입력` 보기를 넣는다). 답이 추천과 같으면 그대로, 다르면 반영해 생성

6. **glab으로 생성** — `-R` 미지정 시 **현재 디렉토리 git remote 의 레포 기준**으로 생성한다 (자동, 묻지 않음. glab 기본 동작과 동일). 사용자가 `-R`/"repo는 X" 로 명시했을 때만 다른 레포 사용:
   ```
   glab issue create -t "<제목>" -l "<라벨1>,<라벨2>,<라벨3>" [-d "<본문>"] [-R <repo>]
   ```
   재작성이면 `create` 가 아니라 `update` 다 — `## 재작성 모드` 를 따른다

7. **이슈 생성 결과 수집**: 이슈 번호 + URL

8. **이슈 note 작성 — 딱 한 번, 적을 게 있을 때만** (형식은 아래 `## 이슈 note 형식`)

    `~/.claude/notes/<group>/<repo>/issue-<N>.md` 에 그냥 쓴다 — git 과 무관하다(커밋·MR diff 없음).

    - **계약 4에서 뺀 상세가 여기 들어간다.** 페이로드 계약·타입·에러코드·호출 순서처럼
      **이미 정해둔 게 있을 때만.** 없으면 이슈만 남기고 파일을 만들지 않는다(빈 뼈대는 노이즈)
    - `<group>`/`<repo>` 는 `-R <group>/<repo>` 인자에서, 없으면 `remote get-url origin` 에서
    - 쓰기 전에 `mkdir -p ~/.claude/notes/<group>/<repo>`
    - ⚠️ **이 파일을 쓰는 건 여기가 처음이자 마지막이다** — 이후 아무 스킬도 갱신하지 않는다
      (규율 문서 `## 상세는 이슈가 아니라 note 에`)

9. **최종 출력**:
    ```
    ✓ 이슈 생성: #<N> <제목>
      <이슈 URL>

    ✓ 이슈 note: ~/.claude/notes/<group>/<repo>/issue-<N>.md      ← 쓴 경우만

    다음 단계 — 워크트리·브랜치 만들고 plan 받기:
      /wtflow:plan <N>

    → wtflow:plan 이 이 세션을 워크트리로 자동 진입시킨 뒤(EnterWorktree)
      plan 을 출력한다. (수동 `claude --worktree` 불필요)
    ```

⚠️ **브랜치 이름을 여기서 정하지 않는다.** accumulator 이름(`<prefix>/#<N>-<slug>`)의 유도와
생성은 전부 `/wtflow:plan` 몫이다 — 이 스킬이 이름을 정해도 넘길 채널이 없어(세션이 끊기면
사라진다) 양쪽이 slug 를 따로 유도하는 결과만 남는다. **소유자를 하나로 둔다.**

## 재작성 모드 (`--rewrite <N>`)

이미 있는 이슈의 **본문(필요하면 제목)을 다시 쓴다.** 조사하며 문제 정의가 바뀌었을 때 쓴다.
이 모드가 없으면 재작성이 스킬 밖 `glab issue update` 직접 호출로 새어나가고, 생성 때 걸리던
계약이 통째로 통과된다.

### 계약을 어디까지 다시 타나

| 생성 계약 | 재작성에서 |
|---|---|
| 1 prefix 추정 | **제목을 바꿀 때만.** 본문만 고치면 건드리지 않는다 |
| 2 라벨 3종 | **적용 안 함** — 이미 붙어 있다. 사용자가 명시할 때만 조정 |
| 3 제목 생성 | **제목을 바꿀 때만.** 생성과 같은 Subject 규칙 |
| 4 본문 작성 | **그대로 적용** — 템플릿 헤더 고정, 서술 절은 목록, 근본원인·코드경로·설계 금지, 자족성 |
| 5 사용자 확인 | **질문 축이 바뀐다** — 아래 `### 확인 질문` |
| 6 glab 호출 | `create` 대신 `glab issue update <N> -d "<전체 본문>" [-t "<새 제목>"]` |
| 7 번호 수집 | **적용 안 함** — 이미 정해져 있다 |
| 8 note | **적용 안 함** — note 는 이슈 생성 때 1회 쓰는 스냅샷이라 재작성에서 손대지 않는다 |

### 절차

1. **현재 본문을 먼저 읽는다** — `glab issue view <N> --output json` 의 `description`·`title`.
   실패하면 중단·보고. ⚠️ **읽지 않고 쓰지 않는다** — `-d` 는 전체 본문 치환이라 통째로 덮어쓰게 된다
2. **템플릿을 읽는다** — `## 본문 템플릿` 의 1~2 그대로. 현재 본문이 템플릿과 어긋나 있어도
   **임의로 맞추지 않는다.** 어긋난 절은 3의 미리보기에 드러내고 사용자가 정한다
3. **미리보기 + 확인** — 아래 `### 확인 질문`
4. **반영** — 본문은 파일을 거쳐 넘긴다. 줄바꿈·백틱·따옴표가 섞이므로 인자에 직접 이어붙이지 않는다
   (`wtflow:mr` 계약 10 과 같은 이유):
   ```
   glab issue update <N> -d "$(cat <본문파일>)"
   ```
5. **출력** — 이슈 URL + 3에서 낸 변화 수치를 실제 반영값으로 다시 한 줄

### 확인 질문

**질문 축은 라벨·prefix 가 아니라 "본문 이대로 반영할지" 다.** 생성과 갈리는 유일한 지점이다.
`AskUserQuestion` 으로 묻는다(산문 나열 금지, 보기 첫째에 `(추천)`).

미리보기에는 **셀 수 있는 변화**를 함께 낸다 — "간결하게" 는 검사할 수 없지만 이건 셀 수 있다:

| 항목 | 형태 |
|---|---|
| 절 수 | `6개 → 6개` (안 바뀌면 `변화 없음`) |
| 줄 수 | `15줄 → 18줄 (+3)` — 목록·단계 줄 기준 |
| 템플릿에 없는 절 | 이름을 전부 나열. 없으면 `없음` |
| 지워지는 절 | 이름을 전부 나열. 없으면 `없음` |

- **템플릿에 없는 절이 1개라도 생기면 그 사실만으로 되묻는다** — 지어낸 절이 소리 없이 들어가는
  것이 실제로 일어난 사고다(템플릿 외 절 3개)
- 줄이 늘면 **늘어난 분량이 무엇인지 한 줄로 적는다**. 그게 계약 4 가 금지한 것(근본원인 분석·
  코드 경로·세부 작업분해)이면 **묻지 말고 다시 쓴다** — 물어서 통과시킬 대상이 아니다
- 관측되지 않은 사실로 절을 채우지 않는다. 사례·수치를 지어내느니 그 절을 비워 둔다

## 이슈 note 형식

`~/.claude/notes/<group>/<repo>/issue-<N>.md`. 계약 8 이 **한 번만** 만든다.
**착수 전 사고의 스냅샷**이지 유지되는 문서가 아니다 — 분량 제한 없이 규격을 못박는 게 목적:

```markdown
---
issue: <N>
repo: <group>/<repo>
created: 2026-08-18             # 상대날짜 금지 — 낡음을 판단하는 기준이 된다
---

## 배경          무슨 문제를 왜 푸는가 + 범위·전제 (2-4문장)

                엔드포인트 | 페이로드(필드·타입·필수·기본) | 에러코드 | 호환성·배포 순서
                확정 안 된 필드는 행을 지어내지 말고 `(미정)`

## 열린 질문      아직 안 정한 것 + 재검토 트리거 (있을 때만)
```

- 표에 담기는 건 **규격**이지 구현이 아니다 — 함수 본문·쿼리를 옮겨오지 않는다
- ⚠️ **K 번호·작업 항목·완료 여부·체크박스 금지** — 진행 상태의 진실원은 이슈 체크박스와 mirror 분기다
- **`branch:`·`milestone_note:` 는 넣지 않는다** — 브랜치 이름은 `plan` 이, 마일스톤은 이슈의
  배정이 각각 답한다. 여기 적으면 답이 둘이 된다
- 마일스톤 계약과 겹치는 내용은 **복사하지 않는다** — 원본이 바뀔 때 사본이 조용히 낡는다

## 본문 템플릿

1. **템플릿 탐색 — 두 경로를 다 본다** (Glob). 한쪽만 보면 다른 호스트의 레포에서 템플릿이
   **있는데도** 없다고 판단해 절을 지어낸다(이게 가장 흔한 실패다):
   - `.gitlab/issue_templates/*.md`
   - `.github/ISSUE_TEMPLATE/*.md`

   둘 다 있으면 remote 호스트에 맞는 쪽(`github.com` → `.github/`), 호스트를 못 가리면 `.github/`
2. **prefix → 템플릿 매핑** (있는 것만 적용):
   - `fix:` → `bug.md`
   - `feat:` → `feature.md`
   - `refactor:` → `feature.md` (작업 항목 구조가 적합)
   - `chore:` → `infra.md` (배포·환경·인프라 변경이 다수)
   - `docs:` → `docs.md`
   - `test:` → 템플릿 없이 한 줄 요약
3. **템플릿 채우기** (간결성·헤더 고정 원칙):
   - 템플릿을 Read 해서 섹션 구조 파악. **GitHub 템플릿 머리의 YAML frontmatter(`name:`·`about:`·
     `labels:`)는 본문이 아니다** — 옮겨 적지 않는다. 절 구조는 그 아래 첫 `##` 헤더부터다
   - **헤더 고정**: 템플릿의 헤더를 그대로 쓴다. 추가·삭제·개명 금지 (`상세 설명`을 `배경`으로 개명하거나 `해결 방향` 같은 새 헤더 추가 금지)
     - 예외는 **템플릿이 스스로 지워도 된다고 적어둔 절**뿐이다(예: `bug.md` 의 `환경` — "특정 환경에서만 재현될 때만"). 지운 절을 나중에 되살리지도 않는다 — 되살리면 본문만 자란다
   - **간결성 상한**: 계약 4 의 `서술 절은 목록이 기본` 을 따른다 — 여기 다시 적지 않는다. 코드 경로/클래스명 나열, 근본원인 추론, 해결책 설계 금지
   - **작업 항목/작업 계획**: **큰 틀의 작업 단위**로 작성 (개수 고정 아님 — 작업 성격에 맞게, 보통 2~5개). 세부 단위 분해는 plan 단계 몫. ⚠️ 이 작업 항목이 이후 `/wtflow:plan` plan·`/wtflow:commit` 의 **K 넘버링 기준**이 된다 (작업 항목 N = Step N = K N = mirror 분기 `-00N`). 따라서 각 항목은 독립적으로 commit·검증 가능한 단위가 되도록 잡는다(순수 조사·식별·분석처럼 산출물 커밋이 없는 단계는 항목이 아니라 plan 몫 — "제거 대상 식별" 같은 항목 금지). 큰 단위조차 안 잡히면 placeholder 유지
     - **마크다운 체크박스 `- [ ]` 로, 위에서부터 K 순서(N=1,2,…)대로 한 줄씩** 작성(다른 체크리스트와 섞지 않기) — K 완료 시 N번째 항목이 자동 체크되기 때문. 템플릿이 평문 나열이면 체크박스로 바꿔 적는다
   - **환경**: 특정 환경에서만 발생하는 등 실제 신호가 있을 때만 채움. 코드 레벨 버그처럼 의미 없으면 placeholder 유지 (`서버/브랜치: <서버> / develop` 같은 무의미한 boilerplate 금지)
   - 그 외 정보 부족한 섹션은 **placeholder 그대로 유지** (사용자가 GitLab UI 에서 보강)
   - HTML 주석 `<!-- ... -->` 도 그대로 유지 (작성 가이드)
4. **폴백**:
   - 두 디렉토리 모두 없음 → 한 줄 요약만
   - 매핑된 파일명 없음 (예: `bug.md` 가 `defect.md` 로 명명) → Glob 결과에서 prefix·종류와 유사한 파일명 추정 (`bug|defect|fix` 등). 모호하면 사용자에게 묻기

## 결정·중단 트리거

- glab 인증 실패 → 보고 후 중단
- 현재 디렉토리가 git 워킹트리 아님 + `-R` 미지정 → repo 명시 요청
- prefix 추정 불가 + 사용자 미응답 → 묻기
- 사용자가 확인 단계에서 거부 → 중단
- 그룹을 못 구함(로컬 remote 등) → note 만 건너뛰고 이슈는 유지, 명시 보고
- `--rewrite <N>` 인데 이슈가 없거나 조회 실패 → 중단·보고. **새 이슈를 만들어 대신하지 않는다**
  (번호를 준 건 그 이슈를 고치겠다는 뜻)
- 재작성에서 현재 본문을 못 읽음 → 중단. 기억·대화 맥락으로 본문을 복원해 쓰지 않는다
  (`-d` 는 전체 치환이라 그 순간 원문이 사라진다)

## 짧은 변형

- "fix 로" / "feat 로" → prefix 강제
- "긴급" / "우선순위 높음" → 우선순위 조정
- "쉬움"/"낮음" → `난이도:낮음`, "어려움"/"높음" → `난이도:높음`
- "repo는 X" → `-R X`
- "본문 자세히" → 본문에 맥락 추가 (단, 계약 4 의 서술 절 규칙은 유지 — 상세는 note 로)
- "note 빼고" / "이슈만" → 계약 8 생략
- "이슈 본문 다시 써줘" / "이슈 갱신" / "이슈에 반영해줘" → `--rewrite <N>`
- 재작성에서 "제목도 바꿔" → `-t "<새 제목>"` 함께 (안 주면 제목은 건드리지 않는다)

## 비고

- 글로벌 컨벤션이라 본인이 사용하는 모든 GitLab 프로젝트에 적용
- **전체 라벨 인벤토리** (본인 표준 — 이 값만 사용, 없는 값 생성 금지):
  - 종류: `종류:기능` · `종류:리팩터링` · `종류:버그` · `종류:인프라`
  - 난이도: `난이도:낮음` · `난이도:보통` · `난이도:높음`
  - 우선순위: `우선순위:낮음` · `우선순위:보통` · `우선순위:높음` · `우선순위:긴급`
- 다른 프로젝트에서 라벨 체계가 다를 수 있으니, 의심되면 `glab label list -R <repo>`로 확인 후 조정
