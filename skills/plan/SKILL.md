# /wtflow:plan — 워크트리 작업 시작

**시작 전에 `${CLAUDE_PLUGIN_ROOT}/references/worktree-discipline.md`(브랜치 이름 규칙·K 모델·note 계층)를 읽는다.**

## 작업 문서

이 스킬이 만드는 것은 결국 **워크트리 하나 + 작업 문서 하나**다. 작업 문서는 목표·범위·작업 항목(K)을
담는 곳이고, **이슈가 있으면 이슈 본문, 없으면 note 파일**이다.

| | 이슈 작업 | 이슈 없는 작업 (adhoc) |
|---|---|---|
| 트리거 | 인자가 정수 — `/wtflow:plan 42` | 인자가 문장 — `/wtflow:plan "다크모드 토글"` |
| 식별자 | 이슈번호 `N` | `slug` |
| accumulator (=워크트리 브랜치) | `<prefix>/#<N>-<slug>` | `<prefix>/+<slug>` |
| 워크트리 경로 | `.claude/worktrees/<N>-<slug>` | `.claude/worktrees/<slug>` |
| **작업 문서** | 이슈 본문 (glab) | `.claude/notes/<repo>/adhoc-<slug>.md` |
| 계약 note | `.claude/notes/<repo>/issue-<N>.md` | (작업 문서와 같은 파일) |

- **accumulator 이름이 유일한 입력이다.** `/#` 뒤 정수면 이슈 작업, `/+` 뒤 문자열이면 adhoc.
  이 해석은 wtflow:commit·progress·auto 도 똑같이 쓴다
- **갈리는 건 "작업 문서가 어디 있나" 뿐**이다. K 분해·mirror·커밋·auto 순회는 두 경우가 완전히 같다
- `+` 는 "이슈 없음" 마커이자 accumulator 자동탐지의 걸쇠다. `~`·`^` 는 git refname 금지문자라 못 쓴다

## 호출

`/wtflow:plan [<이슈번호> | "<작업 설명>"] [-b <base>] [-p <prefix>] [-r <repo>]`

| 인자 | 뜻 |
|---|---|
| `<이슈번호>` (정수) | 이슈 작업. 워크트리 안이면 생략 가능(accumulator·경로에서 N 추론). 워크트리 안에서 **다른 번호**를 명시하면 그 이슈용 워크트리를 새로 판다(계약 2) |
| `"<작업 설명>"` | adhoc — 이슈를 찾지도, 만들지도 않는다 (`## adhoc 작업 시작`) |
| 없음 | 워크트리 안이면 현재 accumulator 에서 자동 추론. 워크트리 **밖**이면 무슨 작업인지 한 줄 되묻고 그 답으로 adhoc 진입 |
| `-b <base>` | 분기 베이스. 미지정 시 `origin/develop`(없으면 `origin/main`) |
| `-p <prefix>` | 브랜치 prefix (accumulator·mirror 공통). 미지정 시 note frontmatter `branch:` > 이슈 종류 라벨(`종류:버그`→`fix` / `종류:기능`→`feat` / `종류:리팩터링`→`refactor` / 그 외 `chore`) > adhoc 은 작업 성격 추론 |
| `-r <repo>` | glab repo (예 `<org>/<repo>`). 미지정 시 git remote 에서 추론 |

## 계약 (보장되어야 하는 것)

1. **대상 확정** — 인자 형태로 이슈/adhoc 을 가르고(위 표), 작업 문서를 확보한다.
   - 이슈 작업 → `glab issue view <N> -R <repo>` 로 제목·라벨·본문. **실패 시 중단·보고**
   - adhoc → `glab` 을 부르지 않는다. `## adhoc 작업 시작` 의 질문으로 목표·범위를 확정하고,
     그게 이슈 본문 자리를 대신한다. 워크트리 안이면 accumulator 의 slug 로 기존 note 를 로드
   - 인자 없음 + 워크트리 안 → accumulator 에서 추론. **accumulator 탐지**:
     ```
     git branch --list '*/[#+]*' --format='%(refname:short)' | grep -vE -- '-[0-9]{3}$'
     ```
     (accumulator 와 mirror 는 같은 prefix 를 쓰므로 `-<KKK>` 유무로 가른다) → HEAD 와 ancestry 를
     공유하는 것이 accumulator

2. **워크트리 판별** — `git rev-parse --show-toplevel` + `git worktree list` 로 현재가 main 워킹트리가
   아닌 워크트리인지 보고, **현재 워크트리의 식별자와 요청을 비교**한다.

   | 상황 | 처리 |
   |---|---|
   | 워크트리 밖 | 3·4·5(신규 셋업) → 6~9 |
   | 워크트리 안 + **다른 작업** 요청 | 현재 워크트리는 그대로 두고 3·4·5 로 **새 워크트리**를 판 뒤 진입 → 6~9 |
   | 워크트리 안 + 같은 작업 + 진행 이력 없음 | 3·4·5 skip → 6~9 (최초 플랜) |
   | 워크트리 안 + 같은 작업 + 진행 이력 있음 | 3·4·5 skip → `## 재플랜 모드` |

   - "진행 이력 있음" = 작업 항목 일부 완료 **OR** mirror 분기(`<accumulator>-<KKK>`)·브랜치 고유 커밋 존재
   - ⚠️ **다른 작업 요청이어도 현재 워크트리 브랜치를 체크아웃/이동하지 않는다.** 격리된 워크트리를
     추가로 팔 뿐이라 글로벌 "워크트리 이탈 금지" 와 상충하지 않는다

### 3~5. 신규 워크트리 셋업 (워크트리 밖, 또는 다른 작업 요청일 때만)

3. **이름 안 제시 + 사용자 확인 한 번** — accumulator 이름은 위 `## 작업 문서` 표 그대로.
   - **여기가 이 브랜치의 생성 지점이다** — wtflow:issue 는 이름만 정하고 만들지 않는다
   - note frontmatter `branch:` 가 있으면 **그대로 쓴다**. 없을 때만 새로 유도 — slug 를 양쪽에서
     따로 만들면 어긋난다. `#` 때문에 브랜치명은 **항상 따옴표로 감싼다**(adhoc 도 형태를 맞춘다)
   - ⚠️ prefix 에 **`worktree/` 를 쓰지 않는다** — 이 이름이 그대로 mirror base 이고 머지 커밋
     메시지에 남는다
   - 경로엔 `#`·`+` 를 넣지 않는다 (`#` 는 셸 주석 문자라 따옴표가 빠지면 조용히 잘린다)
   - slug 는 제목/작업 설명의 한국어를 의미 기반 영어 kebab-case 로(최대 5단어).
     **adhoc 은 slug 가 유일 식별자**라 기존 accumulator·note 와 겹치면 되묻는다(`-2` 자동 접미 금지)

4. **브랜치 + 워크트리 생성**
   - `git fetch origin <base>` 후 `git worktree add <경로> -b "<accumulator>" origin/<base>`
     — 브랜치 생성과 워크트리 부착을 한 번에. **accumulator 이름을 반드시 명시**해야 mirror 가 붙는다
   - **같은 이름 브랜치가 이미 있으면 재사용이 기본** — 사용자가 미리 만들어 둔 마커일 가능성이 높다.
     `-b` 없이 `git worktree add <경로> "<accumulator>"` 로 붙이고 tip·base 대비 ahead/behind 를 보고.
     **되묻는 건 그 브랜치가 이미 다른 워크트리에 물려 있을 때뿐**

5. **세션 진입** — `EnterWorktree({ path })` 로 현재 세션을 **인플레이스 이동**. `cd` 와 달리
   CWD·시스템프롬프트·메모리·plans 캐시까지 워크트리 기준으로 정리된다.
   - ⚠️ `claude --worktree` 금지 — 새 세션을 spawn 하고 브랜치명을 `worktree-…` 로 제멋대로 지어
     컨벤션을 깨고 mirror 가 붙을 곳을 잃는다

6. **계획 문서 로드 (plan 출력 전 필수)** — 이미 정해진 계약이 있는지 먼저 본다.
   - a. 계약 note(`issue-<N>.md` / `adhoc-<slug>.md`)가 있으면 Read — plan 표의 근거
   - b. frontmatter 에 `milestone_note` 가 있으면 그것도 Read. **안 읽고 짠 plan 은 다른 이슈와
        계약이 어긋난다.** 심링크라 다른 세션이 고친 것도 항상 현행으로 보인다
   - c. 둘 다 없으면 건너뛴다 — **마일스톤을 찾아 나서지 않는다**(`glab` 마일스톤 조회 금지).
        `milestone_note` 가 없으면 마일스톤은 없는 것이다
   - 로드한 계약은 plan 표의 "관련 파일/위치"·각 K 설명에 반영하고, 계약과 충돌하는 분해를 내지 않는다

7. **작업 정의 출력** — 작업 문서의 내용(이슈 본문 / adhoc 의 확정된 목표·범위·제외)을 후속 작업의
   컨텍스트로 표시. 코드 분석 시작 안내만 하고 수정은 사용자 승인 후

8. **plan 출력** — 작업 정의 + 계약 6 의 계획 문서 + **코드 분석 결과**로 작업 단계 추정
   (`## plan 출력 형식`). 자동 실행 안 함, 가이드 용도

9. **note 반영 (저장)** — plan 표를 낸 뒤 note 를 갱신한다. 세션이 끊기거나 컨텍스트가 압축돼도
   K별 계약·파일 위치가 남아 재플랜의 근거가 된다.

   | | `issue-<N>.md` | `adhoc-<slug>.md` |
   |---|---|---|
   | 언제 만드나 | **남길 계약이 실제로 있을 때만**(빈 뼈대는 노이즈) | **항상**(작업 항목의 유일한 기록이라) |
   | 형식 | `/wtflow:issue` `## 이슈 note 형식` | 아래 `### adhoc note 형식` |
   | 갱신 범위 | `K별 계약·위치` 표만 — `이 이슈 고유 결정`·`열린 질문` 절은 보존 | 같음 + `작업 항목` 추가·수정 |
   | 체크박스 | ⚠️ **넣지 않는다** — 진실원은 이슈 체크박스 + mirror (근거: wtflow:milestone `## 이원화 금지`) | **넣는다** — 이슈가 없어 이원화될 상대가 없다 |

   - 이슈 작업에서 note 와 이슈 작업 항목이 어긋나면 **항상 이슈가 이긴다.** note 를 이슈에 맞춰 고친다

## adhoc 작업 시작

이슈를 만들 만큼 정리되지 않았거나 만들 이유가 없는 작업을, **K 분해와 커밋 규율은 그대로 두고**
바로 시작한다. 이슈 본문이 하던 일(목표·범위·작업 항목)을 **질문 + 코드 분석**이 대신한다.

1. **묻기 전에 코드를 먼저 본다** — 작업 설명에서 키워드를 뽑아 Glob/Grep. **코드로 답이 나오는 건
   묻지 않는다.** 질문은 코드에 안 적힌 것(의도·범위·완료 기준)만
2. **필요한 것만 한 번에 묻는다** — `AskUserQuestion` 1회, **최대 3문항**. 보기 첫째가 추천안 `(추천)`.
   자유 입력은 자동 "Other" 로 보장되니 "직접 입력" 보기는 넣지 않는다

   | 질문 | 언제 | 안 물을 때 |
   |---|---|---|
   | **범위·완료 기준** (포함/제외) | 거의 항상 — adhoc 의 핵심 결손 | — |
   | prefix / 작업 성격 | 설명으로 성격이 안 갈릴 때만 | 추론 ("추가"→`feat`, "안 됨"→`fix`) |
   | base 브랜치 | `origin/develop` 이 없거나 다른 흐름을 시사할 때만 | `origin/develop` |
   | 접근 방식 | 갈래가 둘 이상이고 K 분해가 갈릴 때만 | 안 물음 |

   ⚠️ **"이슈를 만들까요?" 는 묻지 않는다** — 이슈 없이 시작하겠다고 이미 고른 것이다
   (나중에 필요하면 `## 이슈로 승격`)
3. **확정 요약 3줄** — 목표 / 범위(제외 포함) / prefix·base·브랜치명
4. 이후 계약 3·4·5 → 6~9 는 이슈 작업과 **동일**. plan 표의 Step = K 이고, 그 K 목록이 곧
   adhoc note 의 `작업 항목` 이 된다

### adhoc note 형식

```markdown
---
branch: <prefix>/+<slug>        # = accumulator = 워크트리 브랜치
base: origin/develop
started: 2026-08-08             # 상대날짜 금지
---

# <작업 한 줄 제목>

## 목표
<왜 하는가 — 1~3줄>

## 범위
- 포함: …
- 제외: …               ← 나중에 스코프 드리프트 판정 기준이 된다

## 작업 항목            ← K 목록 = 진행 상태의 진실원 (이슈 체크박스 자리)
- [ ] 1. <K1 한 줄>
- [ ] 2. <K2 한 줄>

## K별 계약·위치
| K | 계약·결정 | 파일/위치 |
|---|-----------|-----------|
| 1 | … | `path/to/file.ts:42` |

## 열린 질문
- …
```

- **`작업 항목` 섹션명과 `- [ ] <번호>. ` 형태를 지킨다** — wtflow:commit `--done` 과
  wtflow:progress 가 이슈 본문과 **같은 규칙**(섹션 안 위에서 K번째 체크박스)으로 읽는다
- 체크박스는 **wtflow:commit 이 켠다.** plan 은 항목을 만들거나 고칠 뿐 상태를 손대지 않는다
- `milestone_note` frontmatter 를 달면 마일스톤 note 도 같이 로드된다(계약 6-b)

### 이슈로 승격

작업 도중 이슈로 올려야겠다 싶으면 `/wtflow:issue` 로 이슈를 만든 뒤 **이름만 갈아끼운다**
(작업물·커밋은 그대로). **사용자 요청 시에만.**

```
git branch -m '<prefix>/+<slug>' '<prefix>/#<N>-<slug>'            # accumulator
git branch -m '<prefix>/+<slug>-001' '<prefix>/#<N>-<slug>-001'    # mirror 전부
```

그리고 `adhoc-<slug>.md` → `issue-<N>.md` 로 옮기고 **`작업 항목` 체크리스트는 이슈 본문으로 이동**한다
— 이슈가 생기는 순간 진실원이 이슈로 넘어가므로 note 에 남기면 이원화된다.

## 결정·중단 트리거

- 이슈 미존재 / glab 인증 실패 → 보고 후 중단. **adhoc 으로 조용히 넘어가지 않는다**(번호를 준 건
  그 이슈를 쓰겠다는 뜻). 전환할지는 되묻는다
- adhoc slug 가 기존 accumulator·note 와 충돌 → 중단하고 다른 이름 요청(같은 작업의 재개면 그 워크트리로 진입)
- adhoc 작업 설명이 한 단어 수준이라 범위를 못 세움 → **워크트리 만들기 전에** 되묻는다(만든 뒤엔 이름이 굳는다)
- 동일 이름 **브랜치** 존재 → 중단 아님, 계약 4대로 재사용이 기본
- 동일 이름 **워크트리** 존재 → `EnterWorktree({ path })` 로 기존 워크트리 진입
- base fetch 실패 / 현재 디렉토리가 git 워킹트리 루트 아님 → 보고 후 중단
- prefix 추론 실패 → 묻고 대기
- 워크트리 안 + 인자 미지정 + 브랜치명에서 식별자 추론 불가·모호 → 경고 + 진행 여부 확인
  (요청이 **명시**돼 현재와 다를 뿐이면 중단이 아니라 계약 2의 "다른 작업 요청")
- 작업 항목이 조사성이거나 코드 분석만으로 대상 확정이 안 됨 → plan 표 **전에** 되묻기

## 짧은 변형

- "이슈 없이 시작" / "이슈 만들지 말고 바로" → adhoc
- "베이스는 main 으로" → `-b origin/main` · "feat 로" → `-p feat`
- "plan 빼고" → 계약 8·9 생략 (작업 정의만 출력)
- "plan만 간단히" → 코드 분석 없이 작업 정의 + 계획 문서로만
- "note 저장 안 함" → 계약 9 생략
- "계약 확인" / "마일스톤 계약 보여줘" → 계약 6만 실행하고 로드한 계약 출력

## plan 출력 형식

### 절차

1. **키워드 추출** — 작업 정의에서 도메인 명사·함수명·파일명·에러 메시지·클래스명 등
2. **관련 파일 탐색** — 파일명/경로 패턴은 Glob(`**/*Annotation*.kt`), 함수·식별자·에러 메시지는 Grep.
   결과는 "관련 파일/위치" 열에 `file:line` 으로
3. **Step = 작업 항목** — 한 작업 항목 = 한 K = 한 mirror 분기, 커밋은 그 안에 누적
   - **작업 항목이 이미 있으면**(이슈 본문 / 기존 adhoc note) **그대로 Step 으로 매핑**한다
     (항목 N = Step N = K N). 코드 분석은 새 step 을 만드는 게 아니라 각 항목의 "관련 파일/위치"를
     채우는 용도
   - **없으면 여기서 만든다**(adhoc 의 첫 plan 이 항상 여기다) — 확정한 범위 + 코드 분석 결과를
     `### step 분할 감각` 으로 쪼갠 것이 곧 K 목록이자 작업 문서의 `작업 항목` 이 된다.
     **표를 낸 뒤 "이 분해로 갈까요?" 한 번 확인**한다
   - 한 항목이 단독 commit 으로 감당 안 될 만큼 크면 보조 분해(하위 a/b)하되 **K 는 항목 번호에 고정**
4. **표 출력** (Step 열 = 작업 항목 번호 = K):

| Step | 설명 | 관련 파일/위치 | 권장 호출 |
|------|------|----------------|-----------|
| 1 | <한 줄 요약> | `path/to/file.kt:42`, `path/to/other.kt` | `/wtflow:commit "<커밋 메시지>" -K 1` |
| 2 | ... | ... | `/wtflow:commit "..." -K 2` |

### step 분할 감각 (작업 항목을 새로 만들 때)

- **bug**: 재현 → 원인 격리 → 수정 → 회귀 테스트. 보통 2-4 step
- **feature**: 데이터 모델/계약 → 핵심 로직 → 통합/UI → 테스트. 보통 3-6 step
- **refactor**: AS-IS 식별 → 변환 전략 → 단계별 변환(의존성 역순). 가변
- **infra/chore**: 단일 commit 으로 충분한 경우가 많다 — 굳이 쪼개지 말기
- **공통**: 한 step = 단독 commit·revert 가능한 최소 의미 단위. 너무 잘면 noise, 너무 크면 회복 어려움

### K 안 태스크(커밋) 분할 — `Na` 라벨

한 K 가 명백히 **여러 논리 변경**을 품으면(리팩터 → 기능 → 테스트) 2~4개 commit-sized 하위 태스크를
`Na`(1a·1b…)로 쪼개 적는다. 같은 K 에 커밋을 누적하라는 뜻 — 새 K 가 아니다.

```
| 2 | 토큰 자동 갱신 도입 | auth/token.ts | /wtflow:commit "..." -K 2 |
    └ 2a (리팩터) 만료 체크 분리   → /wtflow:commit "refactor(auth): ..." -K 2
    └ 2b (기능) 자동 갱신 로직     → /wtflow:commit "feat(auth): ..." -K 2
```

- **힌트일 뿐 — 강제 계약 아님.** 커밋 경계는 구현하며 달라진다. 실제 분할은 wtflow:auto/구현자 판단
- 하위 태스크가 새 K 처럼 보여도 **K 번호는 작업 항목에 고정**(2a·2b 모두 `-K 2`, mirror `-002`)
- 작은 K 는 하위 태스크를 적지 않는다 — noise
- **`Na` 는 plan 출력·커밋 메시지 전용** — 작업 문서의 `작업 항목` 엔 K(N)만 (체크는 `--done` 이 K 단위로)

복잡한 plan/일반 작업 분해가 필요하면 워크트리 무관한 일반 작업 분해 도구를 별도로 쓴다

## 재플랜 모드 (워크트리 안 + 진행 이력 있음)

방향이 바뀌었거나 일부 완료된 뒤 다시 부를 때. **처음부터 다시 그리지 않고 현재 상태 기준 델타 플랜**을
낸다(기존 작업 롤백 안 함).

0. **note 로드** — 계약 6 과 동일. 재플랜에서 특히 중요하다(컨텍스트가 압축돼도 K별 계약이 남아 있다).
   단 **이슈 작업에선 진행 상태를 note 에서 읽지 않는다** — 상태는 1번에서만 온다
1. **진행 상태 수집**
   - 체크박스 — 작업 문서에서(`glab issue view <N> --output json` 의 description / `adhoc-<slug>.md` 의 `작업 항목`)
   - K 진행 — mirror 분기로 집계: `git branch --list '<accumulator>-[0-9][0-9][0-9]'`. 번호=K, tip=최신 커밋
   - 세션 진행 — 대화 맥락상 완료된 작업 / 새로 생긴 방향
2. **완료 접기** — 완료된 항목·K 는 `✓` 한 줄 요약만
3. **스코프 드리프트 처리** (plan 표 **전에**) — 실제 작업이 작업 항목을 벗어났으면 되묻는다:
   (a) 이 브랜치에 **새 K로 이어붙이기** / (b) **작업 항목에 추가**(승인 후 이슈 또는 note 수정) /
   (c) **별도 작업으로 분리**(`/wtflow:issue` 또는 새 adhoc 워크트리).
   추측 금지 — 선택에 따라 K 번호·체크박스 동기화가 갈린다
4. **델타 plan 표** — 잔여 항목 + 신규 스코프만. 완료 K 번호는 고정, 신규는 **`max(mirror KKK)+1`** 부터
   (mirror 는 이 브랜치에만 있어 타 작업 K 오염 불가). 재사용·재배치 안 함
5. **출력 순서** — ① 완료 현황(✓) → ② (드리프트 시) 처리 선택 → ③ 델타 plan 표
6. **note 반영** — 계약 9 와 동일. 신규 K 의 계약·위치만 덧붙인다(완료분·이미 켜진 `[x]` 는 손대지 않음)

재플랜은 **커밋·분기 안 함**(항목 추가는 3-(b) 승인 시에만). note 는 git 밖이라 이력 영향 없다.

## K 매핑과 이후 흐름

- **Step 번호 = K 번호 = 작업 항목 번호.** 커밋은 `/wtflow:commit <설명> -K <N>` 이고
  **K=분기, 그 안 태스크마다 커밋해 누적**한다(한 항목을 커밋 없이 한 덩어리로 진행 금지 —
  사용자가 batch 를 명시했을 때만 예외). mirror 는 `<accumulator>-00N`
- 4단계 이상 또는 1주 이상 예상 → 통합 브랜치 + accumulator 패턴 권장. 1-2단계면 분해 없이 커밋 1회
- 각 step 구현이 끝나면 `/wtflow:commit` 은 **모델이 자율 실행**(커밋+미러 자동)하되 **커밋 후 멈춘다**
  — 여러 K 를 이어 순회하려면 사용자가 `/wtflow:auto` 를 호출(모델 자율 다중-K 순회 금지)
- **K 완료 시 작업 문서의 체크박스 자동 체크** — plan 의 K 매핑이 곧 체크박스 순서이므로 K 를
  항목 번호에 정확히 고정할 것. push·MR 생성 시점만 사용자 결정
- plan 은 자주 틀린다 — 진행 중 자연어로 재조정 가능. 그 시점부터 K 번호만 일관되게 유지하고,
  다음 `/wtflow:commit` 호출에 새 K 번호를 직접 지정한다

## 비고

- note 는 훅이 심링크로 꽂아두므로 그냥 읽으면 된다. **이슈 note·마일스톤 note 의 형식과 생성은
  `/wtflow:issue` 계약 12 · `/wtflow:milestone` 몫**이고 이 스킬은 계약 표만 갱신한다.
  **adhoc note 만은 이 스킬이 주인**이다 — 만들 곳이 달리 없다
- 워크트리 브랜치는 origin 에 push 안 함(로컬 전용 작업 공간). origin 에 노출되는 건 mirror 분기뿐
  — **예외는 `/wtflow:mr` 하나다.** MR 은 소스 브랜치가 origin 에 있어야 성립하므로 그 명령이 accumulator 를 올린다
